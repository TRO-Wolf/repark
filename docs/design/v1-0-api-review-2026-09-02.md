## 1. How to answer

| Answer | What it means |
|---|---|
| `<id> yes` | Freeze the surface at v1.0: additive changes only, a breaking change needs a major version. |
| `<id> no` | Stays pre-stable: it may change between 0.x/1.x tags with a changelog line. |
| `<id> yes except <members>` | Freeze everything but the named members, which stay pre-stable. |

**Answered 2026-09-02 (owner):** `R0 yes` — additive-only within a major; a breaking
change to a frozen row needs a major version and a one-minor deprecation shim; unfrozen rows
may change at any minor with a changelog line. Every row's **decision equals its
recommendation**. The frozen names are registered in [v1-0-api-freeze.json](v1-0-api-freeze.json); the policy is [../release.md](../release.md) "Versioning policy".

## 3. The recommendation rules applied

| # | Rule |
|---|---|
| R1 | **YES** — the surface is pinned on every door it reaches and carries no open §7 BACKLOG row. |
| R2 | **YES except `<members>`** — every open BACKLOG row inside the surface is confined to members that can be named and listed. |
| R3 | **NO** — an open BACKLOG row moves the whole surface (export shape, result type, argument contract), or the surface is still landing (format-v3, deferred connectors, engine tuning knobs). |
| R4 | A DECLARED row does not block a YES: it *is* the contract, and changing it after a freeze is itself the breaking change the freeze governs. |
| R5 | The example gate is reported, never thresholded — tree-wide coverage is 67/913 (7.3 %), so a ≥ 90 % examples criterion would refuse all 35 rows; pins and residuals decide, examples stay evidence. |
