The two answers

Copy-on-write is safe for the silver cutover. The production silver tables are format-version 2 with write.merge.mode = copy-on-write; the first hardening pass had only measured merge-on-read. SQL-HARDEN-2 added six rows (CTAS, MERGE twice, overwritePartitions at v2 and v3) and ran them on repark and live Spark 4.1.2, then through the Glue and S3 Tables acceptance legs.

  • No delete file appears under copy-on-write on either engine, on any catalog.
  • Row sets, snapshot operations, second-MERGE idempotence and v3 next-row-id are Spark-equal everywhere.
  • The only divergences are the two metadata classes already on file: column requiredness (CUTOVER-CTAS-REQ-1) and Spark's stamped compression codec (V3-COV-7).

Only one dynamicFlatten optimization is worth building. Measured on a release build with a fair design (eight threads on both engines, materialized inputs, five iterations, a measured 10.8 ms noise floor), each candidate timed in isolation:

CandidateIsolated cost× noise floorVerdict
Null-mask struct extractor (struct depth 6, 30 % null parents minus 0 %)59.98 ms5.5queued · PERF-DYNFLATTEN-2
Cartesian multi-list operator (two lists minus each list alone)26.91 ms2.5closed · at the floor
Optimizer wrapper walks (strongest single fixture)0.45 ms0.04closed

The first debug-build ranking put the Cartesian operator second; release numbers and per-fixture isolation reversed it. Three registry rows came out of the bed: a qualified-name clash at any struct depth ≥ 2 with a sibling keep column, a dropped list<null> column, and parquet-required nullability kept where Spark widens.
