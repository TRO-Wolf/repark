Purpose

A definition, not a gate

The repository uses "production grade" in goals, cards and reviews, but until now it had only an evidence checklist in PROJECT.md and no definition of the term itself. This page is the definition agents and reviewers apply when a capability claims the label, and a rubric for reviewing that claim.

No new ledger, no new check and no required artifact comes from this page. It adds no make target, no script, no CI job and no document a unit must produce. The answers it asks for already live in existing contracts and tests.

The page is permanent and is amended deliberately, never as a passenger on another change. An owner ruling that moves the definition elsewhere retires it.

docs/production-grade.md · Purpose

Definition

What the label claims

A capability is production grade when it delivers its documented behavior within a declared operating envelope, protects data during failures, makes its condition observable, and can be maintained and upgraded with justified confidence, and those claims are backed by repeatable tests and operational evidence.

The compressed heuristic: the number of things you must know that are not written down is close to zero.

The review form of the same idea:

  • the contract is written;
  • the failure paths are tested as thoroughly as the happy path;
  • a stranger reads the code without a guide;
  • a change is cheap because the tests catch what matters;
  • the limits are stated rather than discovered.

Scope

The operating envelope

Production grade is relative to a declared scope: the supported workloads, data sizes, concurrency, storage systems and deployment shapes. A capability is production grade inside its envelope; outside it, the honest behavior is a refusal.

Inside the envelope

RePark is an embedded, single-node, no-JVM engine. Refusing distributed execution or a server mode is inside the envelope, not a gap in it (AGENTS.md "Explicitly out of scope"; PROJECT.md "Not now, and why").

The posture

A clear refusal with a hint beats a plausible wrong answer. That is already the repository's posture: PROJECT.md's "no silent degradation" rule and AGENTS.md's "LOUD unsupported errors" rule.

Assessment

Assessed per capability, never averaged

Local analytical queries, Iceberg writes, the Spark facade, CDC and a future warehouse service have different failure modes and need different evidence. Each is assessed on its own; there is no single score for the engine. Strength in one attribute does not offset weakness in another: excellent documentation does not offset a possible silent data loss.

Part of production grade is exposure to real workloads, and that cannot be bought. The honest claim for a young project is therefore "production grade for the workloads we have exercised", with the list of those workloads as the evidence. A claim without that list is a claim about workloads nobody has run.

Disqualifies

Anti-patterns

Each of these disqualifies a capability from the label however well it is tested. Where the repository already enforces one, the existing rule is named rather than described.

  • Silent fallbacks: a path that quietly takes a slower, looser or different route instead of refusing.
  • Swallowed errors: an error caught and dropped, or downgraded to a log line the caller never sees.
  • Panics in library code: enforced by make rust-panic-ban (AGENTS.md "Hard rules").
  • Hidden global state: held by the everything-through-Session discipline (docs/adr/0004-server-prep-disciplines.md).
  • Undocumented environment variables: any behavior switch a user cannot find in the configuration guides.
  • Nondeterministic or flaky tests: a test that can pass and fail on the same input proves nothing; the testing contract's "Forbidden patterns" name the related escape hatches.
  • Knowledge that lives only in one head: a step, a limit or a reason that exists only in a conversation; AGENTS.md "Write for the eventual reader" says where durable reasons go.
  • A claim of "supported" with no named test: the testing contract (docs/testing.md) requires the test in the same change.

Direction

Values for directing agents and reviewers

  • Evidence over assertionA claim stands on a named test or a recorded measurement, never on agreement.
  • Explicitness over surpriseA user learns a limit from a refusal or a document, never from a wrong answer.
  • Simplicity with purposeEvery abstraction earns its place with a second real caller.
  • Failure is ordinaryCrashes, conflicts and bad input are designed for and tested, not treated as rare.
  • Compatibility is stewardshipData and pipelines that worked yesterday keep working, or the change says so first.
  • Honest limits"Not supported" and "not yet measured" are valid, written answers.
  • Useful observabilityEmit what an operator needs to act on, not everything that happened.
  • Proportionate assuranceThe depth of evidence matches what a failure would cost the user.
  • Learning compoundsEvery incident leaves a pinned test and a written lesson behind.

Review

Five review questions

For any capability that claims the label:

  1. What exactly is promised, and under which conditions?
  2. What can go wrong, and what happens to the user's data and work when it does?
  3. What evidence demonstrates the guarantees?
  4. How does someone diagnose, recover and upgrade?
  5. What remains unproven or unsupported?

The answers live in the existing contracts and tests: the capability's guide, its registry rows in docs/spark-sql-iceberg-parity.md, its pinned tests and its committed baselines. They are not a new artifact, and a reviewer asks them rather than requiring a document that answers them.
