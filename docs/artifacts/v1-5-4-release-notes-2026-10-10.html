Wrong stored value, fixed

One nanosecond wall on every write door

In a session whose time zone is not UTC, INSERT stored the session wall clock into a top-level timestamp_ns column, while several other doors stored the UTC wall for the same value. The table held two different times for one input depending on which statement wrote it.

Before

INSERT OVERWRITE, every MERGE arm, UPDATE SET, overwritePartitions and insertInto(overwrite=True) stored the UTC wall.

Now

Every door stores what INSERT stores, at full nanosecond precision. Run-end-encoded and dictionary-encoded sources store the same wall on the overwrite doors.

Behaviour change

Three writes that now refuse

Each of these stored something before. They now stop with a named error and write nothing.

A nested timestamp_ns value

A write that supplies a value for a column whose type holds a timestamp_ns below the top level (a struct field, an array element, a map key or value) refuses with [INCOMPATIBLE_DATA_FOR_TABLE.CANNOT_SAFELY_CAST]. Before, it stored a value, often the UTC wall. Converting nested values correctly is follow-up work, so this release refuses instead of storing a time that may be wrong.

  • Still works: omitting the column, supplying a bare NULL for it, updating or merging other columns, DELETE, compaction and other maintenance, and every read.
  • Not affected: CREATE TABLE AS SELECT, REPLACE TABLE AS SELECT and CALL system.add_files, which take the source's own values.
  • Also refuses: the same write sent to a branch, under write-audit-publish settings, inside EXPLAIN ANALYZE, or through PREPARE and EXECUTE.
  • Not covered: nested timestamptz_ns and microsecond types behave as in v1.5.3.

An unfiltered UPDATE that would cut nanoseconds

UPDATE with no WHERE refuses when its SET value was narrowed from nanoseconds to microseconds by the expression around it, for example array(c, NULL)[0] or CASE … ELSE NULL. One such spelling stored a truncated, wrong value before; the others raised an unnamed error.

Error text on a malformed write

On a table that holds a nested timestamp_ns column, a write statement that fails to parse reports the nested refusal above where it used to report the parser's message. Other tables keep the parser's message.

PR #1018 · follow-up card ICE-TSNS-NESTED-1

Security

A table with an encryption key refuses its first write

RePark cannot encrypt table data yet. A table that carries the encryption.key-id property now refuses every statement that would write a data, delete, manifest or statistics file, with UnsupportedOperationException. The message names the table and the property and never repeats the key id.

Spark 4.1.2 with Iceberg 1.11.0

Ignores the key on format v3 and writes plaintext without warning.

RePark v1.5.4

Refuses the write on every format version. This is deliberately stricter than Spark.

  • Still works: CREATE, SELECT, time travel, snapshot expiry, orphan-file cleanup, rollback and other pointer moves, ALTER, and unsetting the key, after which writes run again.
  • Unkeyed tables: unchanged. 395 statements compared against v1.5.3, none moved; CPU time within 2%.

Two gaps remain. A rollback or branch move can publish rows that were staged in plaintext before the key was set. A session that loaded the table before the key was added can leave one orphan data file behind before its commit is refused.

Wrong answer, fixed

Join conditions

  • Cross join with a condition. df.join(other, cond, "cross") dropped the condition and returned every pairing. It now answers as the inner join, as Spark does. The recorded case returned 12 rows where Spark returns 2.
  • Conditions Spark rejects. A non-deterministic condition such as rand(), or an untyped NULL condition, now refuses for every join type with Spark's error classes: INVALID_NON_DETERMINISTIC_EXPRESSIONS and JOIN_CONDITION_IS_NOT_BOOLEAN_TYPE. Both the DataFrame and SQL doors refuse.

PR #1010 · merge 153b6cb5

Fixes

Smaller fixes

  • COUNT(*) on change readers. COUNT(*), COUNT(1), SELECT 1, df.count() and EXISTS now answer over the changelog, incremental and lineage readers. They failed with an internal error before. #1017
  • Epoch constructors in SQL. timestamp_seconds, timestamp_millis and timestamp_micros answer on the SQL door as Spark does, including decimal arguments at their boundaries and Spark's refusals for overflow and unsupported argument types. #1012
  • pyarrow floor. The dependency is now pyarrow>=25.0.1. pyarrow 25.0.0 can crash the process on a first collect(), take(), head(), first() or toLocalIterator() called from a thread. The fault is upstream and fixed in 25.0.1. #1015

Upgrading

From v1.5.3

pip install --upgrade repark==1.5.4
  • The API freeze holds; no public name was removed or renamed.
  • pip will move pyarrow to 25.0.1 or later if you are on 25.0.0.
  • If a pipeline writes nested timestamp_ns values, it will now stop with the named refusal. Omit the column, supply NULL, or load through CTAS until the nested conversion ships.
  • If any table carries encryption.key-id, writes to it will stop. Unset the property to write plaintext knowingly.
  • If a non-UTC session wrote top-level timestamp_ns through the overwrite, MERGE or UPDATE doors on an earlier version, check those rows.
