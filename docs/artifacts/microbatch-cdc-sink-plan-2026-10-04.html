The micro-batch change-data sink

Bronze to Silver over Iceberg snapshots: a loop, not a streaming engine. What main already has, the design, the slices, how they parallelise, the ten owner rulings, and the order work opens.

Measured on origin/main at 1060ebeb · markdown of record: task/roadmap/epic-term/microbatch-cdc-sink-plan-2026-10-04.md · owner: "Go with recommendations"; "Catalog only. Sink waits for 1.6. TA first. No deletes in bronze."

1 · What "Flink-like" means here

A source offset per Bronze table, a trigger, one batch per trigger read as an incremental scan between two snapshots, the Silver transform over that batch, one commit into Silver, and the offset advanced atomically with that commit. Flink's heavy parts, keyed operator state and event-time timers, are not needed for a Bronze-to-Silver upsert sink because every piece of durable state lives in an Iceberg table. Latency is the Bronze commit cadence, not sub-second.

3 · The design, D-1 to D-8

  • D-1 Offsets live in the sink. Each micro-batch commit stamps the query id, the epoch and the source snapshot id of every Bronze input into the Silver snapshot summary, and writes the same offset vector as a table property in the same commit. No checkpoint directory for an Iceberg sink. The crash between sink commit and checkpoint cannot happen because there is no second write.
  • D-2 A batch source over the append scan. Next window, caps by files or rows, and a refusal when the window holds an overwrite or delete snapshot: Bronze is append-only by contract (O-5).
  • D-3 A Session-owned driver. A tokio task in repark-core, one batch in flight per query, availableNow and processing-time triggers, the four CC-1 shutdown rules. Its only soft state is the in-flight batch, rebuilt from the sink.
  • D-4 Idempotent replay. The epoch check before commit; the C-008 walk on an unknown outcome; two drivers on one sink are safe because the second loses at the expected-base validation.
  • D-5 Deterministic identity on every record. An event id on Bronze (source generation, table identity, canonical key, source position) and a version id for Silver (the same without the operation), UUIDv5 over canonical typed bytes, a vectorised kernel in repark-common, a RePark-owned function with a dated registry row. Nothing the pipeline minted feeds the hash. It enters the Bronze contract now (O-2).
  • D-6 Catalog-only state. Offsets in the sink, ids computed, the replication slot holding the capture position, OCC plus the generation field for fencing, staged files invisible until commit. A shared catalog is required; a local filesystem catalog refuses a streaming query. A control database earns its place only at multi-writer (2.x).
  • D-7 Two transform doors, foreachBatch first. An existing Silver job body runs unchanged while the runtime owns offsets, triggers and exactly-once; SilverPlan S-2 is the second door. A Silver table fed by several Bronze tables has a vector offset.
  • D-8 The facade. readStream, writeStream, trigger, foreachBatch, StreamingQuery; the SES-DECL rows flip and the three IPI-47 cells get measured. Rust first.
Operational costs, stated up front. A short trigger produces thousands of Silver snapshots a day, so expire_snapshots and compaction policy are part of the design. Merge-on-read sinks need rewrite_data_files on a schedule. One catalog commit per batch per table is the hot path.

4 · Why not one lane, one shot

The build is four to five units the size of ICE-CHANGELOG-1, which landed about 1,750 lines of product Rust and 840 of Python in one day and then needed a remediation round. A verifier reading one PR of that size has no catch rate; the review pipeline is one scoped verifier per product PR and one PR per slice. Every design question is answered from recorded Spark plus Iceberg cells, and the careful ICE-CHANGELOG-1 packet still got two of ten decisions wrong until the lane read the bytecode. Exactly-once is a proof, not a feature, and the harness that proves it decides MB-2's shape. The fork changes are a separate repository and pin cycle. The hours spent on the prompt go into a design packet in the shape of the ATTR-ID-1 design order, so each slice runs in fewer rounds.

10 · Existing Bronze tables and the identity backfill

Filed at the owner's instruction in the wording the owner asked to keep; it answers "will this work with already built bronze tables?"

How it lands on existing Bronze. One schema change per table adds the id column, which in Iceberg is metadata only. One backfill pass then fills it from the existing columns: the source table identity, the primary key, and the version rule. That is a one-time rewrite of each Bronze table through repark, and your Bronze volumes are small. From then on new rows carry the id at write. The alternative is to compute the id on read inside the batch source and never store it in Bronze. Both give identical ids, since that is what deterministic means. I recommend the backfill so the contract is uniform and external readers such as the Glue job and Trino see the same column rather than recomputing it.

The precondition is a version rule per table. Your current Bronze rows carry the source columns plus an ingestion timestamp, an operation type that is always APPEND, a DAG version and a run type. None of the pipeline columns may feed the id. So the event id for the existing tables is the source table plus the primary key plus the source's own version column where the source has one, such as an updated-at field. A table whose source has no version column needs a declared fallback in its Bronze contract, and that fallback has to be something the source row carries, not the extraction date. The capture producer will later use the same per-table rule with the LSN as the version, so the daily Bronze and the capture Bronze of one source table hash the same way. This is the "declared, not inferred" rule the silver compiler already applies to dataset mode.

What the backfill will surface. Rows the daily DAG extracted twice, for instance after a re-run, get the same id. That is the feature, not a bug. The backfill report will show how many duplicates each table already holds, and Silver dedups on the id from the first batch onward. The generation field for existing tables is their current table UUID, so a future drop-and-recreate cannot collide with them.
