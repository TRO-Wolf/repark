Three findings that explain most of it

1 · The Rust caches are warmed in a different environment than they are used in new

The cache-warm workflow's lint and test jobs run without the Python 3.12 setup step that the CI lint and test jobs have. The build scripts of pyo3 and aws-lc-sys fingerprint that environment, so on every code PR cargo discards the restored artifacts for them and everything above them: 66 crates recompiled in the test job (7.3 min, including the aws-lc C build), 145 rechecked in lint (3 to 5 min). The wheel cache, whose warm job does set up Python, works: only the 11 workspace crates compile. Three successive PR runs show the same 66-crate recompile under the same cache key.

2 · Two fixtures are the facade suite's shape your 10-03 ruling

The ten slowest facade tests sum to 687 s against a slowest shard of 691 s. Your 3 October ruling made CI-2 conditional on that ratio exceeding a quarter. It is 99 percent. Two thousand-filter-chain setups account for 470 s: test_deep_subquery_expression_1 (279 s) and test_deep_filter_chain_crash_1 (190 s). Both are setup time, not assertion time.

3 · Test execution is serial where it need not be

Locally the facade target runs one Python process for about 170 minutes; CI runs the same suite with four workers per shard in 12. In the Rust test job, cargo runs the 89 test binaries one after another; four of them hold 386 of the 544 reported seconds (ddl_sessions 171, repark-core 84, repark-iceberg 72, timestamptz_ns_wall_doors 58).

What is already right

Path-filtered changes gate keeps docs PRs at 2 minutes. The ci profile strips debuginfo and incremental state. Concurrency cancels superseded PR runs. Facade shards already use xdist. None of this needs touching.

Reliability and safety guardrails

  • No gate is removed, narrowed or skipped. Required checks, path filters and the test set are unchanged; every item changes how fast the same work runs.
  • Caches cannot create a false green. Cargo reuses an artifact only when its fingerprint matches; a stale or wrong cache costs time and nothing else.
  • One change per PR, measured before the next. The before-and-after numbers go in the PR body so the record is in git, not in a chat.
  • Nextest is more isolation, not less. Each test gets its own process. The first run may expose tests that relied on process-shared state; those get fixed as findings with their own regression proof, never silenced.
  • PA-15 stays exactly as it is. No bound is raised and nothing is serialised to hide it, per the 11 October audit. Nextest's slow-timeout report names it when it stalls.
  • Versions stay pinned. pytest-xdist in the lock, nextest pinned in the Makefile and the workflow, the same way every other CI tool is.
  • Fork CI is left alone. The Windows build is its 24-minute pole, but only Tests default and doc are required (14 and 3.4 min), so it does not block merges.
