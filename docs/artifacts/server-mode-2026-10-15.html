Server mode: the route forward

How RePark should reach a persistent server, read against what the repository has already decided: ADR 0004's adapter posture, the roadmap's protocol order, and the operation lifecycle the engine does not yet have.

Build the operation lifecycle first, then a server core, then Arrow Flight SQL as the first protocol. Treat Spark Connect as the second protocol on the same core rather than the first. The one blocker to settle before any daemon is the sync and async boundary inside the session.

  • Posture already decided

    Server mode is an adapter

    ADR 0004: everything through Session, bindings thin, no ambient state.

  • Roadmap order today

    Connect 1.13, Flight SQL 2.0

    Both on one server core; this page proposes the reverse.

  • Cancellation today

    None

    The facade's interrupt calls return empty lists by design.

  • Sync inside async

    34 measured block_on sites

    Unconditional, in the session, reader and catalog doors.

Where the project stands

  • ADR 0004 made the right bet early. Everything goes through the Session, bindings are thin adapters, and server mode was always meant to be another adapter. That is the single reason a server is tractable now.
  • The roadmap orders the protocols Connect first. Spark Connect at 1.13 as protocol one, Flight SQL at 2.0 as protocol two, both on a server core built once. The 2026-09-30 external review argued for an operation lifecycle before any server, and the roadmap left that discussion open.
  • Three hard problems were deferred to the server milestone. Credential vending, Python UDFs under a shared process, and per-query resource policy. None has started.
  • There is no operation lifecycle. No cancellation, no per-query memory budget separate from the session pool, no timeouts. A server without those is a denial-of-service surface for its own users.

The route

  1. Operation lifecycle in the core, exposed embedded first

    A query handle with a cancel token threaded through DataFusion execution, status, elapsed time, a per-query memory budget drawn from the session pool, a timeout, and results as an Arrow stream rather than a collected batch.

    Why first: it is the concrete driver ADR 0005 was waiting for, and it pays off before any server exists. Ctrl-C in a notebook stops a query, the facade's interrupt family becomes real, and all of it is testable without a network.

  2. Fix the sync and async boundary before writing a daemon blocker

    The v1.5.2 slowdown work measured 34 unconditional block_on sites across the session, reader and catalog doors. A tonic server runs inside a tokio runtime, and block_on from inside a runtime panics.

    What it needs: an audit and a plan for making those paths async-native. This is architecture, not a task list, and it deserves a design sketch before anyone builds.

  3. The server core, decomposed only as far as the server needs

    A session manager keyed by connection, a query service, shared catalog caches, and the server-side resource policy. Execute the ADR 0005 slices the server actually calls and no others. Credentials are configured server-side from repark.toml, so clients never carry them. Python UDFs refuse in server mode on day one; Rust-native UDFs stay first-class.

    Why this scope: ADR 0005 deferred the decomposition until a real caller wanted a specific cut. The server is that caller.

  4. Flight SQL as protocol one first protocol

    SQL in, Arrow out, a well-specified protocol with a mature Rust crate. It unlocks JDBC, ODBC, BI tools and a standalone binary at once, and it exposes only the SQL door, which keeps the surface small. Authentication is mTLS and bearer tokens as the roadmap already lists.

    Label: ships experimental under the production-grade page's envelope rule, with the exercised workloads named.

  5. Spark Connect as protocol two, started as a measurement second protocol

    The spike the roadmap already describes: one pinned client, AnalyzePlan and ExecutePlan over reads, projection, filter, join and aggregate, everything else refusing with a named class, scored on the migration scorecard.

    Why second: most of Spark Connect's cost is not the server. It is an analyzer that maps proto relations onto RePark plans with the same name resolution, coercion and refusal rules the facade registry carries today.

Why Flight SQL before Spark Connect

The server core is about eighty percent of the work for either protocol and is identical for both. Flight SQL adds a thin handler on top. Spark Connect adds a thin handler plus a second implementation of Spark semantics. Putting Flight SQL first means the core is proven under real connections before the harder analyzer work starts, and it gives the project a daemon, auth and operability story a year earlier.

Spark Connect remains the bigger product bet, since unchanged pyspark clients are the thesis, and it loses nothing by going second on a proven core. This reverses the current 1.13 and 2.0 order, so it is the owner's call, and the migration scorecard is the evidence that should decide it.

What stays out

  • Distribution. Fleet-parallel, then server, then distributed only if a query outgrows one box is still right. Serving and distributing are different problems, and the distributed crate is not the serving path.
  • Multi-writer across processes. One server process serializes Iceberg commits per table, the simplest correct model until the 1.13 multi-writer work.
  • Governance features. Masking, row filters and audit depend on a server existing and wait for one.

The honest risks

  • The session is one large object and the server is the first caller that needs it decomposed. Reversible internal work, but it touches every door.
  • Caches and credentials assume one user per process. A shared process needs per-session isolation of both, and credential vending is unsolved.
  • Memory. Never-OOM and spill assume one session owns the pool. Fair sharing across sessions is new policy, not new mechanism, and needs its own torture runs.

The first unit to charter

The operation lifecycle plus the block_on audit, as a design sketch before any build. Both answer questions every later slice depends on, and both improve the embedded product on their own.
