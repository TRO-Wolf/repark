2 · Why the wall is three times the arithmetic

Sixteen workers sharing 62 minutes of test time should finish in four. They took fifteen. The reasons are mechanical, and each was confirmed by an experiment rather than inferred.

Contiguous chunks put the heavy files on one worker

pytest-xdist's default load scheduler hands each worker an opening block of len(tests) / workers / 4 consecutive cases, 323 here, and tops up in blocks of up to 647. Collection order is alphabetical by file, so the three nanosecond files that sit together (tsns_floor_doors, tsns_merge_wall, tsns_type_planner, 21 minutes of work) land on one or two workers while the rest sit idle. CI's shard 6 exists for exactly this reason; this is the same effect inside a shard.

Module fixtures are rebuilt on every worker that draws a cell

A module-scoped fixture is built once per worker per module. When a module's parametrised cells are spread across workers, each worker builds it. The struct-pairing replay showed up fifteen times in the slowest-durations list at 24 workers, 65 to 79 seconds each; the deep-subquery fixture was built on four workers under work stealing, 25 worker-minutes for six tests. 34 files carry a module- or session-scoped fixture; 20 of those also parametrise.

Each worker thinks it owns the box

The engine's Tokio runtime sizes itself to the visible cores and DataFusion's partition count defaults to the same, so sixteen workers plan sixteen-by-26-way parallel queries on 26 cores. That is why 24 workers ran slower than 16 under the default scheduler. A global four-partition cap through REPARK_CONFIG shaved a minute but broke 71 tests that set or count partitions themselves, so it is not a knob to turn globally.

What it is not

Not fsync: 785 calls in 98 seconds of Iceberg tests cost 42 milliseconds in total. Not sleeps: the suite's 32 sleep calls add up to about ten seconds. Not session construction: 0.4 milliseconds after the per-test reset, 0.25 seconds for the first query in a process, 22 milliseconds for a small createDataFrame plus collect.

4 · Session consolidation, revisited

The 2026-10-03 ruling closed this as a speed item, and the measurement agrees: a session is free. What the survey found is an organisation problem wearing a performance costume.

  • 300 of 535 files define their own session fixture. 290 of them normalise to 89 distinct bodies; 74 are byte-identical apart from the app name (builder.appName().getOrCreate(), yield, stop). 209 call sites add a .config() and genuinely need their own session.
  • conftest has no RePark session fixture at all. Its only session-scoped fixture is the live PySpark oracle engine. An autouse fixture resets the process-wide active session around every test, so independent sessions are already the contract; a shared fixture would be function-scoped and change nothing about isolation.
  • What a shared fixture would buy: one place to set the warehouse, the temp directory and any future default; new files from any worker tier that look alike; roughly a thousand lines gone. What it would not buy: a single second of wall time.
  • What Sail does: one module-scoped spark fixture in a package conftest, shared by code tests and doctest transcripts. Polars has no session concept and builds frames inline.

Recommendation. Add spark and spark_with_warehouse(tmp_path) fixtures to conftest and have new files use them; leave the 290 existing copies alone unless you want a mechanical clerk pass over the 74 identical ones. Not a unit on its own; it rides along with the config change in section 6.

Two things in the comparison matter more than the rest. Polars keeps a fast inner loop by tiering, not by having fewer tests: the default command skips what is slow or writes to disk, and CI runs everything. Sail keeps the suite navigable by subsystem directories with their own conftest, so a session fixture is written once per area. RePark has neither, and its one directory is now larger than both of theirs put together.

7 · Decisions that are yours

1 · The 2026-10-03 ruling

It said no test-migration and no fixture-consolidation units, CI-2 only on measured durations. Items 1 to 5 above stay inside it (flags, one-line marks, config, one file's fixture). Item 6 and any fixture migration do not. Say which parts of the ruling stand.

2 · Items 1 to 4 now?

Four clerk-grade PRs, each measured in its body, none touching an assertion. Together they take the local facade from 24 minutes to under seven minutes for the full run and a few minutes for the fast tier.

3 · The directory move

Yes, no, or later. If yes: all at once on a quiet day, or one area per PR.

4 · The deep-subquery fixture

It is the floor under every scheduler. Splitting it is the one change here that edits what a test builds, which is why it is listed separately under the CI-2 clause.
