Decisions for you

  1. 1. A killed CTAS on S3 Tables leaves an empty table (blocks the scoped label)

    On S3 Tables, RePark creates the table first and drops it if the query fails. A kill skips the drop, so the catalog lists an empty table under the user's name (run 43126006620). Glue leaves nothing, and ordinary failures leave nothing on either catalog.

    Options:

    • A (default): refuse CTAS and REPLACE … AS on S3 Tables, as Spark very likely does. First, one live Spark CTAS cell.
    • B: a temporary name, then a rename. This is a new design, and the place where a Fable consult would help.
    • C: keep RePark's CTAS on S3 Tables and exclude it from the label.

    Spark's own CTAS on S3 Tables is still unmeasured; the matrix's CTAS cells use local Spark values.

  2. 2. New S1: decimal plus double in a UNION or VALUES writes a wrong value

    RePark types 0.1 UNION ALL CAST(1e-20 AS DOUBLE) as decimal(30,15), where Spark types it double. INSERT … SELECT … UNION ALL … into a DOUBLE column then stores 0.0 instead of 1e-20.

    • Large doubles overflow, where Spark answers.
    • A negative zero loses its sign.
    • Plain INSERT … VALUES is correct.
    • The existing card COALESCE-NAN-DOUBLE-1 has the same root.

    Default: open DECIMAL-DOUBLE-UNION-COERCION-1 as the next lane unit, after signed-zero PR B or ahead of it (your call).

  3. 3. The p15 truth column in the matrix harness

    For d = 0.0 in DML, the committed Spark-on-Iceberg answers are the zero-only pruned ones (PRUNED-WRONG under ruling G). So RePark's current answer matches them, and the strict xfail markers XPASS. Once part A merges, these cells would read as wrong.

    Default: a small harness PR that takes p15's expected value from the truth rule (Spark SQL semantics), and labels Spark-on-Iceberg's answer as the declared divergence.
