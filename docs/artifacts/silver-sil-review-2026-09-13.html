SIL-1 name the first bronze table. SIL-4 choose opt-in validation or a fork change. Everything else can take its recommended default.

How to read a card

Each card says what the decision is, what S-0 measured, the recommendation, and the exact question left for you. A green tag means the default is safe to accept as written.

The one measured trap

RePark's default overwrite isolation is snapshot. Under it, an overwrite that lands after a concurrent append silently deletes the appended file, and setting commit.retry.num-retries=0 does not stop the first-attempt rebase. That is correct Spark parity for ordinary overwrites. It is wrong for silver publication, so whatever you rule on SIL-4, the publish path arms validate_no_conflicting_data. Probes: overwrite without validation committed deleted-data-files=2; with validation it refused as non-retryable DataInvalid and the concurrent head stayed.

The rulings

SIL-1

First dataset and the supported type matrix

needs your input
Deciding
Which bronze table silver classifies first, and the finite set of types and operations the first plans may use.
Measured
Seven types round-trip Iceberg to Arrow and back at the pin: int32, int64, utf8, bool, date32, timestamp-microseconds UTC, decimal128. Keys and source order on int32, int64 and utf8 (bytewise) sort totally. Four of the five plan operations already exist as engine functions: Trim as btrim(col, ' '), EmptyToNull as nullif, RequireNonNull as isnotnull, CheckAllowedValues as in_list. ParseTimestamp with a parse-success flag is missing; the engine has no format parse that reports success separately from null.
Recommend
Start with exactly that matrix. Keep ParseTimestamp out of the first plans until S-2 builds the kernel.
Your call
  • Which bronze table goes first, with its key field, source-order field and stable record-id field named.
  • Decimal cap: accept Decimal128 with precision up to 38, or restrict further.
  • ParseTimestamp: waits for S-2, or the first table must not need it.
SIL-2

Invalid latest version

accept the default
Deciding
What happens when the newest version of a keyed record fails classification.
Measured
Nothing to probe in storage; this is plan semantics from the proposal's section 10.
Recommend
Latest-source-version wins. An invalid latest version quarantines the key. Silver never falls back to an older valid row, because that would publish a state the source no longer asserts.
Your call
  • Yes to that default, or you want fallback to the last valid version.
SIL-3

Ordering conflicts and repeats

accept the default
Deciding
What silver does when two rows tie for greatest version, when keyed history cannot be ordered, and when identical payloads repeat.
Measured
Plan semantics only; no storage probe.
Recommend
Fail the run on a conflicting tie or an unorderable history. Identical repeats resolve to the lowest bronze record id.
Your call
  • Accept fail-on-conflict.
  • Canonical payload equality: compare every non-key field exactly, or compare a hash of them. Exact is recommended until S-9 sets a budget.
SIL-4

Publication primitive

needs your input
Deciding
How a silver run stages files, gates them, commits them conditionally, and later proves it published.
Measured
All four steps work at the pin with no fork change. Data files write with no catalog commit and can be handed to a later commit. One overwrite-by-always-true replaces the whole table in one snapshot. A run key rides that snapshot's summary and is findable from metadata alone. The commit-outcome taxonomy is clean: conflict is retryable, a validation refusal is non-retryable, a lost response is CommitStateUnknown and is never auto-retried. Two traps: the rebase above, and the fork will not let a caller pin an expected-base snapshot independently of refresh.
Recommend
Build the publish function in the existing write adapter beside overwrite_commit.rs: hold the expected-base table, stage, gate, then overwrite with validate_no_conflicting_data, validate_from_snapshot(base) and the run key as a snapshot property. On an unknown outcome, walk snapshots for the run key and never retry a replace. No fork change.
Your call
  • Opt-in validation is enough (recommended), or you want a first-class expected-base commit in the fork, card F-SILVER-PIN-BASE.
  • The run-key property name. The probe used repark.silver.run-key.
SIL-5

Consumer interface

accept the default
Deciding
What readers see and how they pin a run.
Measured
The single-snapshot full replace is proven, so one committed snapshot id is a complete publication point.
Recommend
One classified physical table. The committed snapshot id is the read handle.
Your call
  • How plain SQL consumers bind a run: by snapshot id (recommended, it already works through time travel), by a branch per run, or by filtering on the run key as a column.
SIL-6

Retention and quarantine

accept the default
Deciding
How long a run stays provable and where quarantined rows live.
Measured
Expiring a snapshot removes its summary, so a run key that lives only there disappears with it. A replay window longer than snapshot retention cannot resolve an ambiguous commit from metadata alone.
Recommend
Set snapshot retention to cover the retry and replay window, or dual-write the run key into table properties in the same transaction. Physical file cleanup stays a separate maintenance step.
Your call
  • The replay and retry window in days.
  • Dual-write the run key into table properties: yes or no.
  • Where quarantined rows are readable from.
SIL-7

Quality gate limits

accept the default
Deciding
When a run is allowed to publish.
Measured
Staging without commit makes it possible to run every gate on the exact files that would publish, so a failed gate leaves the last accepted snapshot current with nothing to roll back.
Recommend
Gates run on staged files before commit; a failure publishes nothing.
Your call
  • Denominators for rates: all bronze rows, or classified rows only.
  • Thresholds for the first table.
  • Empty input: publish an empty table, or refuse.
  • Whether losing evidence rows blocks publication.
SIL-8

Module ownership

accept the default
Deciding
Which crate owns the plan, the compiler and the publisher.
Measured
The crate graph puts repark-core at tier 2 above repark-iceberg at tier 1. S-1 already landed the plan contract under repark-core/src/silver/ on that basis.
Recommend
Plan, policy and compile in repark-core; the publish adapter in repark-iceberg's write module; Python stays a thin authoring door. No new crate.
Your call
  • Module under repark-core now (recommended), or wait for a later crate split.
SIL-9

Performance budget

accept the default
Deciding
What silver must cost before an implementation is judged.
Measured
Nothing yet; S-0 deliberately asserted no target.
Recommend
Set the methodology first: the hardware, the corpus and how a run is timed. Only then set memory and latency budgets.
Your call
  • The corpus. The proposal names a 190-column set; confirm it or name another.
  • Budgets can wait until the first measured run.
SIL-10

Schema evolution

accept the default
Deciding
What happens to consumers when a plan's output shape changes.
Measured
Proposal section 13; no storage probe.
Recommend
A fixed output contract per accepted plan. A breaking change needs either a versioned target table or a reviewed migration.
Your call
  • Versioned target (recommended, it keeps every published snapshot readable as-is) or reviewed migration.
