A dropped table's rows come back after drop and recreate on the Hadoop catalog

S1 candidate silent wrong read not carded · not ruled fork rev 66901f02 · main aacefc82
RePark returns the rows of a dropped table; Spark returns the right rows.

This happens on a type=hadoop catalog, in one session, through the ordinary SQL door, with no error. The cause is located: a staged replace in the iceberg-rust fork leaves a metadata cache entry behind. Hadoop names metadata files v1, v2 and so on, and those names come back when a table is recreated. Glue and S3 Tables are not affected, and turning the cache off gives the right answer.

The reproduction

CREATE TABLE hd.ns.t (id BIGINT, n INT) USING iceberg;
INSERT INTO hd.ns.t VALUES (7, 1);
CREATE OR REPLACE TABLE hd.ns.t AS SELECT CAST(id AS BIGINT) AS id, 1 AS n FROM range(2, 5);
DROP TABLE hd.ns.t;
CREATE TABLE hd.ns.t (id BIGINT, n INT) USING iceberg;
CREATE OR REPLACE TABLE hd.ns.t AS SELECT CAST(id AS BIGINT) AS id, 1 AS n FROM range(2, 5);
SELECT count(*), min(id), max(id) FROM hd.ns.t;

The trigger: the dropped table's history contains a replace, and the recreated table's commit at the reused version number is also a replace.

The cause

Read from the fork's source at rev 66901f02. Paths are relative to the root of the TRO-Wolf/iceberg-rust repository.

The cache key is the file path

table_metadata_cache.rs: the key is (scope, location), at line 142. A hit is re-checked only when both object versions are known (line 155). The memory catalog passes none, so a hit is never re-checked. RePark turns the cache on by default with 512 entries (repark-iceberg/src/catalog/caches.rs:44).

Hadoop names are reused

Hadoop naming writes v1, v2 and so on. A recreated table starts again at v1. Glue, S3 Tables and the default memory naming put a UUID in each file name, so they never reuse a path.

Normal commits keep the cache clean

memory/catalog.rs update_table invalidates the previous location (line 606) and caches the new one (line 608). drop_table invalidates only the current location (line 459).

The staged replace does neither

memory/staged_publish.rs:82 publish_replace swaps the pointer and nothing else. It never drops the base location it replaced from the cache, and never caches the location it wrote. Compare publish_create_hadoop, which caches at line 72.

  1. In C,I7,R, the insert caches v2. The replace publishes v3 and leaves v2 in the cache.
  2. The drop invalidates only v3, so v2 survives. It holds the dropped table's state after the insert.
  3. The recreated table's replace writes a new v2 and caches nothing.
  4. The next load of v2 hits the dead entry and reads the dropped table.

Scope

affected

  • Hadoop catalogs, in one session.
  • Every later read of the recreated table. Whether later writes build on the stale base is not measured (question 2).
  • My reading, not ruled: this blocks the full format-v2 label at S1.

not affected

  • Glue and S3 Tables, because metadata file names carry a UUID.
  • The scoped Glue and S3 Tables label.
  • A fresh session or process.

workaround

repark.iceberg.metadataCache=false gives the right answer (measured).

Proposed fix (not ruled)

Card LOCAL-DROP-RECREATE-STALE-READ-1, S1. It would block the full v2 label and not the scoped one. The fix would be one fork PR and one RePark pin.

  1. Replace keeps the cache clean. publish_replace does what update_table does: it drops the base location it replaced from the cache and caches the location it wrote.
  2. Drop clears the whole chain. Under Hadoop naming, drop_table invalidates every location in the dropped table's chain, not only the current one.
  3. Optional extra guard. A lookup could check the cached table uuid against the pointer. Alternatively, local files could carry an object version (size and mtime) so the existing check can fire.
  4. Pins. Every wrong row above becomes a cell checked against Spark. A fork unit test asserts that a replace and a drop leave no stale entry. The purge row must read right instead of failing.

Questions for the agent

  1. Are fixes 1 and 2 both needed, or is one enough and the other a guard? Is fix 3 worth its cost on a read path that has performance gates?
  2. Can a write whose commit base comes from the stale entry, such as a MERGE after the stale replace, persist wrong data? If so, the severity rises to a wrong write.
  3. Do other fork catalogs' replace or create paths have the same missing invalidate or put? With UUID names that leaks memory but does not return wrong rows.
  4. Within one table's life, can a Hadoop vN path ever be written twice, through a retried commit or a version-hint race?
  5. Should a Hadoop-named DROP TABLE simply clear the whole cache for that catalog?
