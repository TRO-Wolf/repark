# CAST-cost attribution — PERF-CAST-1 step 1 (2026-09-12)

Where a `CAST` costs a millisecond. Measurement only; no product change
(card D-1). The S2-21 reviews measured ~1.4–2.7 ms per CAST physical
expression and superlinear blow-up in wide plans. This document is the
table that says **which phase** owns that wall.

This file closes when PERF-CAST-1 merges, or when the owner closes the
slate row.

## C-001 — wall by shape × CAST count

`plan` is `session.sql` (parse + analyzer + optimizer + DataFrame wrap).
`execute` is `EXPLAIN ANALYZE … .collect()` (plans again, then evaluates,
discards the result). `total = plan + execute`.

| shape | casts | plan median (s) | execute median (s) | total median (s) | SQL bytes |
|---|---:|---:|---:|---:|---:|
| standalone | 50 | 0.094 | 2.028 | 2.120 | 1,749 |
| standalone | 250 | 0.385 | 10.165 | 10.544 | 9,049 |
| standalone | 2500 | 3.958 | 99.287 | 103.410 | 95,299 |
| over_aggregate | 50 | 0.101 | 0.876 | 0.976 | 1,899 |
| over_aggregate | 250 | 0.773 | 4.845 | 5.627 | 9,799 |
| over_aggregate | 2500 | 38.969 | 136.947 | 175.878 | 102,799 |
| projection_over_aggregate | 50 | 0.096 | 0.277 | 0.372 | 1,930 |
| projection_over_aggregate | 250 | 0.357 | 1.001 | 1.357 | 9,830 |
| projection_over_aggregate | 2500 | 3.623 | 10.181 | 13.819 | 102,830 |

Per-CAST plan at 250 over_aggregate: 0.773 / 250 = **3.1 ms**, matching the
reviews' 1.4–2.7 ms band on a quieter / different shape. At 2500 the same
ratio is 38.969 / 2500 = **15.6 ms** — the per-expression cost itself grows.

The 200k-row standalone execute (~99 s at 2500) is linear evaluation of
200k × 2500 Utf8 CASTs. The reviews' 0.12 s "250-cast standalone" was a
literal SELECT (plan-dominated). Both numbers are in the table.

## C-003 — which phase is superlinear

Log-log least squares, `time ≈ a × casts^b`, three sizes.

| shape | plan exponent | execute exponent | total exponent |
|---|---:|---:|---:|
| standalone | 0.959 | 0.994 | 0.994 |
| over_aggregate | **1.535** | 1.302 | 1.339 |
| projection_over_aggregate | 0.934 | 0.928 | 0.930 |

**Named phase:** logical-plan construction of a wide CAST-over-aggregate
(`over_aggregate` `session.sql`), exponent **1.535**. Standalone projection
and CAST-over-a-one-row-aggregate are linear / slightly sublinear. Execute
for `over_aggregate` is 1.30 because `EXPLAIN ANALYZE` re-plans (~39 s)
before the 81 s of `elapsed_compute`.

## C-002 — where the 2500-cast wall goes

One attribution pass per shape at 2500 CAST. `datafusion.optimizer.max_passes`
0 / 1 / 3 each on a fresh session.

### over_aggregate × 2500 (the superlinear cell)

| phase | seconds | note |
|---|---:|---|
| sql_string_build | 0.0008 | Python text only |
| sql_parse_literals_same_width | 0.546 | `SELECT 1 AS c0, … c2499` — parse + plan of the same list width, no CAST |
| logical_and_physical_plan | 38.724 | `session.sql` of the CAST aggregate |
| plan_max_passes_0 | 38.797 | optimizer loop skipped |
| plan_max_passes_1 | 38.916 | one optimizer pass |
| plan_max_passes_3 | 39.055 | DataFusion default |
| explain | 111.696 | logical + physical plan text, no execution |
| explain_analyze | 138.891 | re-plan + evaluate |
| explain_analyze_elapsed_compute | 81.021 | sum of DataFusion `elapsed_compute` |
| physical CAST count | 2500 | in the ANALYZE dump |
| ANALYZE plan text | 386,902 B | |

`max_passes` 0 / 1 / 3 agree to 0.3 s. **No optimizer pass owns the 39 s.**
The 0.55 s same-width literal SELECT leaves ~38 s in analyzer + logical
expression construction of 2500 `CAST(sum(id + i) AS VARCHAR)` slots.

`EXPLAIN` (111.7 s) is ~73 s above `session.sql`: physical expression
creation plus rendering 387 KB of plan text. Per-batch evaluation of the
one-row aggregate is the 81 s `elapsed_compute`, not the superlinear term.

### Analyzer / optimizer / physical pass names

`EXPLAIN VERBOSE` of over_aggregate × 50 (99 `plan_type` rows). Optimizer
passes run and are named; they do not move the 2500-cast `session.sql`
wall (`max_passes=0` matches `max_passes=3`).

Analyzer (before `analyzed_logical_plan`): `resolve_grouping_function`,
`higher_order_preparation`, `type_coercion`, `sliding_frame_rescan`
(repark), `repark_insert_store_assignment`, `spark_integer_literal`,
`lambda_rebind`, `spark_decimal_precision`, `spark_decimal_rewrite`,
`spark_nullability`, `spark_integer_overflow`, `spark_expr_semantics`,
`array_cardinality_ceiling`, `spark_ltz_timestamp_cast`,
`bool_decimal_cast`.

Optimizer (DataFusion default list, up to `max_passes=3`):
`rewrite_set_comparison`, `optimize_unions`, `unions_to_filter`,
`simplify_expressions`, `replace_distinct_aggregate`, `eliminate_join`,
`decorrelate_predicate_subquery`, `scalar_subquery_to_join`,
`decorrelate_lateral_join`, `extract_equijoin_predicate`,
`eliminate_duplicated_expr`, `eliminate_filter`, `eliminate_cross_join`,
`eliminate_limit`, `propagate_empty_relation`, `filter_null_join_keys`,
`eliminate_outer_join`, `push_down_limit`, `push_down_filter`,
`single_distinct_aggregation_to_group_by`, `eliminate_group_by_constant`,
`common_sub_expression_eliminate`, `extract_leaf_expressions`,
`push_down_leaf_projections`, `optimize_projections`.

Physical: `OutputRequirements`, `aggregate_statistics`, `join_selection`,
`LimitedDistinctAggregation`, `FilterPushdown`, `EnforceDistribution`,
`CombinePartialFinalAggregate`, `EnforceSorting`, `OptimizeAggregateOrder`,
`WindowTopN`, `ProjectionPushdown`, `LimitAggregation`,
`LimitPushPastWindows`, `HashJoinBuffering`, `LimitPushdown`,
`TopKRepartition`, `PushdownSort`, `EnsureCooperative`,
`FilterPushdown(Post)`, `SanityCheckPlan`.

The analyzed plan expands each `id + i` to
`__repark_spark_int_add__(CAST(id AS Int64), CAST(Int64(i) AS Int64))`
before the outer `CAST(sum(…) AS Utf8View)`. That is the spark-integer
analyzer, not an optimizer rule. It triples the CAST count in the
analyzed tree versus the SQL text; it is present on standalone too, which
stays linear, so the **aggregate wrapping** is what goes superlinear.

### Profile (2500-cast over_aggregate `session.sql`)

`py-spy record --native --rate 99`, 6868 samples, ~69 s wall (session
build + sql). `perf record` is not usable on this box
(`perf_event_paranoid=4`).

Symbolized samples cluster on:

- `foldhash` / `hashbrown` hashing (`write_num<u64>`, `write_usize`)
- `datafusion_common::tree_node::TreeNode::apply` / `maybe_grow`
- `datafusion_optimizer::analyzer::type_coercion::TypeCoercionRewriter`
- `sqlparser` `parse_cast_expr` / `parse_select_item` (small; matches the
  0.55 s same-width literal probe)
- most of `_native.abi3.so` unsymbolized (debug module, 660 MB)

Optimizer rule bodies do not appear. That agrees with `max_passes=0`.

Session plan-time probes: `py.entry` spans (`PyReparkSession.sql` vs
`PyDataFrame.__arrow_c_stream__`). `sql()` is the 39 s wrap; collect /
ANALYZE is the execute side.

## C-006 — who owns the superlinear phase (step 2)

`crates/repark-core/tests/cast_plan_profile.rs` (`#[ignore]`d; run under
`cargo test --release`) times `session.sql` of the same CAST-over-aggregate
statement phase by phase, twice: once on a stock `SessionContext` (no Spark
extension, no repark analyzer rules or function registrations) and once on a
`ReparkSession` context. Same 200k-row MemTable, same statement, medians of
three after a warmup. Wall-clock run: 80.9 s total.

`SqlToRel::statement_to_plan` (`sql_to_rel`) against CAST count:

| arm | 50 (s) | 250 (s) | 2500 (s) | log-log exponent |
|---|---:|---:|---:|---:|
| stock | 0.0024 | 0.0307 | 2.7434 | **1.81** |
| repark | 0.0024 | 0.0310 | 2.7378 | **1.81** |

All phases at 2500 casts:

| phase | stock (s) | repark (s) |
|---|---:|---:|
| parse (sql_to_statement) | 0.0171 | 0.0154 |
| **sql_to_rel (statement_to_plan)** | **2.7434** | **2.7378** |
| analyzer execute_and_check (all rules) | 0.0901 | 0.0915 |
| optimizer optimize (all rules) | 0.2522 | 0.2498 |
| `SessionContext::sql` end-to-end | 2.7545 | 2.7469 |
| create_physical_plan | 0.4650 | 0.4793 |

Per-rule walls at 2500 (repark arm; stock agrees): analyzer —
`type_coercion` 0.0797 s, `sliding_frame_rescan` 0.0011 s,
`resolve_grouping_function` 0.0016 s (the other repark spark rules are
sub-millisecond). Optimizer — `optimize_projections` 0.0588 s,
`simplify_expressions` 0.0450 s, `common_sub_expression_eliminate` 0.0152 s,
each of the other 21 default rules ≈ 0.008–0.010 s. No single rule is
superlinear; `sql_to_rel` is 96 % of the planning wall.

Three variant probes isolate what inside `sql_to_rel` is slow (2500-wide,
medians):

| variant | stock (s) | repark (s) |
|---|---:|---:|
| `DataFrame::aggregate` of 2500 `sum(id + i)` (builder, no SQL) | 0.0117 | 0.0117 |
| bare `sum(id + i)` aggregate **without CAST** through `sql_to_rel` | 2.6942 | 2.6886 |
| standalone `CAST(id + i)` projection through `sql_to_rel` | 0.0376 | 0.0377 |

**Verdict: upstream DataFusion.** Stock and RePark arms agree to ~1 % on
every phase, so no repark analyzer rule, extension, or Spark function
registration owns the wall. The discriminant is the builder row: the same
2500-expression aggregate assembled through `DataFrame::aggregate` takes
12 ms while the equivalent SQL takes 2.7 s inside `statement_to_plan`, and
the bare aggregate without CAST is equally superlinear — the cost is in
`SqlToRel`'s SQL-expression-to-`Expr` path for a wide `Aggregate`
(TreeNode construction / expression hashing, matching the step-1 py-spy
symbols), not in CAST and not in the logical `Aggregate` node itself.

The pin is not re-based: `wheels.yml` builds the PR/main wheel debug and
the `ci.yml` parity job runs without a native module (the cast pins
`importorskip`), so the pin never executes on release in CI; the
debug-derived budget stays, and the strict xfail stays armed for a
DataFusion bump to flip.

## Upstream issue (filed as [apache/datafusion#25248](https://github.com/apache/datafusion/issues/25248), 2026-09-12)

`datafusion.optimizer.max_passes` 0 / 1 / 3 are the same wall (debug 39 s),
and step 2's micro-bench shows the whole `optimize` stage is 0.25 s on
release — no optimizer rule owns it, so this unit sets no knob and changes
no engine code. Issue text as filed:

---

**Title:** `SqlToRel::statement_to_plan` is superlinear for a wide `Aggregate` (exponent ≈ 1.8, DataFusion 54.1.0)

**Body:**

Planning `SELECT CAST(sum(id + i) AS VARCHAR) AS ci …` with N slots over a
200 k-row, one-column `Int64` MemTable is superlinear in N on a release
build of DataFusion 54.1.0, on a stock `SessionContext` with no extensions:

| N | parse (s) | `statement_to_plan` (s) | analyzer (s) | optimizer (s) | `ctx.sql` (s) |
|---:|---:|---:|---:|---:|---:|
| 50 | 0.0004 | 0.0024 | 0.0007 | 0.0049 | 0.0027 |
| 250 | 0.0015 | 0.0307 | 0.0039 | 0.0235 | 0.0323 |
| 2500 | 0.0171 | 2.7434 | 0.0901 | 0.2522 | 2.7545 |

`statement_to_plan` alone is 96 % of `sql()` at N = 2500 and fits
`time ∝ N^1.81` over the three sizes (per-rule timing shows every analyzer
and optimizer rule near-linear). Three discriminators:

- The same N-expression aggregate built through
  `DataFrame::aggregate(Vec::new(), exprs)` — no SQL — takes **0.012 s** at
  N = 2500, so the logical `Aggregate` node itself is cheap.
- A bare `sum(id + i)` aggregate **without** any CAST shows the same
  superlinear `statement_to_plan` (2.69 s at 2500), so CAST is not the
  amplifier.
- A same-width standalone `CAST(id + i)` *projection* plans in 0.038 s —
  the blow-up is specific to the wide `Aggregate` SQL path.

`datafusion.optimizer.max_passes` 0 / 1 / 3 does not move the wall.
A `py-spy --native` profile of the same `sql()` clusters on
`foldhash`/`hashbrown` hashing, `TreeNode::apply`, and
`TypeCoercionRewriter`. Suspected mechanism: an O(N)-per-expression
TreeNode walk or hash inside `SqlToRel`'s aggregate expression handling
(qualify/normalize per select item).

Minimal reproduction (Rust, release): register a one-column `Int64`
`MemTable` named `t` on a stock `SessionContext`, then time
`state.statement_to_plan(state.sql_to_statement(&sql, "generic").await?)`
for `SELECT` of N items `CAST(sum(id + i) AS VARCHAR) AS c{i}`.

---

The flip pin stays a strict xfail on the superlinear plan phase; a
DataFusion release that fixes this turns it green without a RePark diff.
