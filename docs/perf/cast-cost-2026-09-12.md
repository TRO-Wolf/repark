## C-001 — wall by shape × CAST count

`plan` is `session.sql` (parse + analyzer + optimizer + DataFrame wrap).
`execute` is `EXPLAIN ANALYZE … .collect()` (plans again, then evaluates,
discards the result). `total = plan + execute`.

| shape | casts | plan median (s) | execute median (s) | total median (s) | SQL bytes |
|---|---:|---:|---:|---:|---:|
| standalone | 50 | 0.094 | 2.028 | 2.120 | 1,749 |
| standalone | 250 | 0.385 | 10.165 | 10.544 | 9,049 |
| standalone | 2500 | 3.958 | 99.287 | 103.410 | 95,299 |
| over_aggregate | 50 | 0.101 | 0.876 | 0.976 | 1,899 |
| over_aggregate | 250 | 0.773 | 4.845 | 5.627 | 9,799 |
| over_aggregate | 2500 | 38.969 | 136.947 | 175.878 | 102,799 |
| projection_over_aggregate | 50 | 0.096 | 0.277 | 0.372 | 1,930 |
| projection_over_aggregate | 250 | 0.357 | 1.001 | 1.357 | 9,830 |
| projection_over_aggregate | 2500 | 3.623 | 10.181 | 13.819 | 102,830 |

Per-CAST plan at 250 over_aggregate: 0.773 / 250 = **3.1 ms**, matching the
reviews' 1.4–2.7 ms band on a quieter / different shape. At 2500 the same
ratio is 38.969 / 2500 = **15.6 ms** — the per-expression cost itself grows.

The 200k-row standalone execute (~99 s at 2500) is linear evaluation of
200k × 2500 Utf8 CASTs. The reviews' 0.12 s "250-cast standalone" was a
literal SELECT (plan-dominated). Both numbers are in the table.

## C-003 — which phase is superlinear

Log-log least squares, `time ≈ a × casts^b`, three sizes.

| shape | plan exponent | execute exponent | total exponent |
|---|---:|---:|---:|
| standalone | 0.959 | 0.994 | 0.994 |
| over_aggregate | **1.535** | 1.302 | 1.339 |
| projection_over_aggregate | 0.934 | 0.928 | 0.930 |

**Named phase:** logical-plan construction of a wide CAST-over-aggregate
(`over_aggregate` `session.sql`), exponent **1.535**. Standalone projection
and CAST-over-a-one-row-aggregate are linear / slightly sublinear. Execute
for `over_aggregate` is 1.30 because `EXPLAIN ANALYZE` re-plans (~39 s)
before the 81 s of `elapsed_compute`.

## C-002 — where the 2500-cast wall goes

One attribution pass per shape at 2500 CAST. `datafusion.optimizer.max_passes`
0 / 1 / 3 each on a fresh session.

### over_aggregate × 2500 (the superlinear cell)

| phase | seconds | note |
|---|---:|---|
| sql_string_build | 0.0008 | Python text only |
| sql_parse_literals_same_width | 0.546 | `SELECT 1 AS c0, … c2499` — parse + plan of the same list width, no CAST |
| logical_and_physical_plan | 38.724 | `session.sql` of the CAST aggregate |
| plan_max_passes_0 | 38.797 | optimizer loop skipped |
| plan_max_passes_1 | 38.916 | one optimizer pass |
| plan_max_passes_3 | 39.055 | DataFusion default |
| explain | 111.696 | logical + physical plan text, no execution |
| explain_analyze | 138.891 | re-plan + evaluate |
| explain_analyze_elapsed_compute | 81.021 | sum of DataFusion `elapsed_compute` |
| physical CAST count | 2500 | in the ANALYZE dump |
| ANALYZE plan text | 386,902 B | |

`max_passes` 0 / 1 / 3 agree to 0.3 s. **No optimizer pass owns the 39 s.**
The 0.55 s same-width literal SELECT leaves ~38 s in analyzer + logical
expression construction of 2500 `CAST(sum(id + i) AS VARCHAR)` slots.

`EXPLAIN` (111.7 s) is ~73 s above `session.sql`: physical expression
creation plus rendering 387 KB of plan text. Per-batch evaluation of the
one-row aggregate is the 81 s `elapsed_compute`, not the superlinear term.

The analyzed plan expands each `id + i` to

analyzer, not an optimizer rule. It triples the CAST count in the
analyzed tree versus the SQL text; it is present on standalone too, which
stays linear, so the **aggregate wrapping** is what goes superlinear.

### Profile (2500-cast over_aggregate `session.sql`)

`py-spy record --native --rate 99`, 6868 samples, ~69 s wall (session
build + sql). `perf record` is not usable on this box
(`perf_event_paranoid=4`).

Symbolized samples cluster on:

- `foldhash` / `hashbrown` hashing (`write_num<u64>`, `write_usize`)
- `datafusion_common::tree_node::TreeNode::apply` / `maybe_grow`
- `datafusion_optimizer::analyzer::type_coercion::TypeCoercionRewriter`
- `sqlparser` `parse_cast_expr` / `parse_select_item` (small; matches the
  0.55 s same-width literal probe)
- most of `_native.abi3.so` unsymbolized (debug module, 660 MB)

Optimizer rule bodies do not appear. That agrees with `max_passes=0`.

Session plan-time probes: `py.entry` spans (`PyReparkSession.sql` vs
`PyDataFrame.__arrow_c_stream__`). `sql()` is the 39 s wrap; collect /
ANALYZE is the execute side.

## D-2 — not a RePark optimizer knob; draft upstream issue

`datafusion.optimizer.max_passes` 0 / 1 / 3 are the same 39 s, so this
unit does not set a DataFusion optimizer knob and does not change
repark-core this round.

The superlinear work sits in DataFusion logical-plan construction
(analyzer type-coercion + TreeNode walk + expression hashing) of a wide
`Aggregate` of CAST expressions. RePark's spark-integer analyzer adds
inner CASTs; it is not the superlinear *shape* (standalone has them and
is linear). Step 2 either lands an upstream DataFusion issue with these
numbers, or a repark-side planner change if a later isolation names one
analyzer rule. Draft issue text (do not file — the orchestrator does):

---

**Title:** Superlinear logical-plan construction for wide `CAST(sum(…) AS Utf8)` aggregates (exponent 1.54 at 50 / 250 / 2500)

**Body:**

Planning `SELECT CAST(sum(id + i) AS VARCHAR) AS ci …` with N slots over a
200 k-row MemTable is superlinear in N on DataFusion 54.1.0:

| N | `SessionContext.sql` (s) | `EXPLAIN` (s) |
|---:|---:|---:|
| 50 | 0.10 | ~0.9 execute-inclusive in our wrap |
| 250 | 0.77 |  |
| 2500 | 38.97 | 111.7 |

Log-log exponent of `sql()` vs N is **1.535**. Setting
`datafusion.optimizer.max_passes` to 0, 1, or 3 does not change the 39 s
(optimizer rules are not the cost). A same-width `SELECT 1 AS c0, … c2499`
plans in 0.55 s, so SQL parse of the select list is not the cost either.

`EXPLAIN VERBOSE` names the usual analyzer (`type_coercion`, …) then the
default optimizer list; py-spy `--native` of the 39 s `sql()` shows
`TypeCoercionRewriter`, `TreeNode::apply`, and foldhash/hashbrown hashing.
A 2500-expression *projection* of the same CASTs over `sum(id)` is linear
(~3.6 s), so the blow-up is the wide `Aggregate` of CAST expressions, not
CAST in general.

Reproducer: DataFusion 54.1, 2500 `CAST(sum(col + i) AS Utf8) AS ci` in one
`SELECT` over `generate_series` / a MemTable. Happy to attach the plan.

---
