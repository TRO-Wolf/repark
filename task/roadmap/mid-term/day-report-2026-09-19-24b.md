## 3. What the measurements showed

- **Page pruning found a silent wrong answer already on main (#310 r2).** A `_pos` or `_row_id` projection decodes whole files, and that path decoded only the projected columns. A predicate on an unprojected column therefore evaluated as false on every row: Spark's v3 table with `i > 1800` returned 0 rows where Spark returns 199. Only the Spark-written fixture exposed it. Fixed in #310.
- **Java's `rewrite_table_path` produces stale sizes.** Delete files rewritten by it keep a stale `file_size_in_bytes` in the manifest. The reader now retries a failed footer read once at the real length (Java uses `InputFile.getLength`), and only for a footer-read failure.
- **Java's `rewrite_table_path` refuses shared DV puffins.** It cannot rewrite a v3 table whose DV puffin serves several data files (`AlreadyExistsException` on the second blob). The fixture was re-recorded with one DELETE per data file.
- **Q-24b-1 (declared).** All-null pages are skipped for `<`/`<=`. This matches Java's `ParquetMetricsRowGroupFilter`, parquet-mr's column-index filter, SQL three-valued logic and the fork's own row-group evaluator. Through SQL the answer is Spark's with the knob on and off. At the core `TableScan` door, the knob-on scan excludes NULLs that the fork's nulls-first residual would keep. Pinned at both doors.
- **parquet-mr drops the column index of a double column holding NaN.** One Spark fixture file has none for `d`. Before #310 made missing indexes select all pages, such a file would have failed any filtered scan with the knob on.
- **The fork writer's page defaults equal Java's.** parquet-rs 58.4 uses 20,000 rows and 1 MiB per page. My 07:13 claim that fork-written files have one page per chunk was wrong; I corrected it in claims at 09:31. What is missing is honouring user-set `write.parquet.page-row-limit` / `page-size-bytes` / `row-group-size-bytes` — a parity item, not claimed.
- **F-PAGE-PRUNE-2 (#319) mechanism, measured first.** On a release bench with the fork writer (50 files × 128k rows, 16 pages per chunk), the evaluator (~5 µs/file) and the index parse (~7 µs/file) were noise. The cost was elsewhere:
  - an all-keep `RowSelection` forces parquet-rs 58.4 into a sparse per-page fetch and decode, about 150 µs/file;
  - a loaded offset index switches `SerializedPageReader` into Pages mode under a RowFilter, about 0.7 ms/file.

  Dropping an all-keep selection and stripping the index for the scan brings the non-prunable ON/OFF ratio from 1.274 to 1.003, and the prunable ratio of ~0.63 is kept.
- **F-TS-PUSHDOWN-1 (#312).** DataFusion hands the provider `TimestampMicrosecond(v, Some("UTC"))` for a Spark `TIMESTAMP` literal; converting it to `timestamptz` is enough to bind. 24a's bed measured the win (§1).
- **F-EXACT-COUNT-1 (#317).** Java's `pushAggregation` sums `planFiles()` record counts and has no residual check; the fork's rule is stricter. Summing per task double-counts a split file, which the 64-way split pin proves.

## 5. Owner questions (with recommendations)

1. **Q-24b-A: fork writer honours `write.parquet.*`.** The fork honours only the compression codec and level. Java honours page-row-limit, page-size-bytes, row-group-size-bytes and dict-size-bytes. *Recommendation:* a parity card, fork-side, with RePark's own INSERT `WriterProperties` routed through the same helper, as 24d's F-METRICS-CONFIG-1 did for metrics.
2. **Q-24b-B: the core-door nulls-first residual.** The fork's `RecordBatch` residual treats `NULL < x` as true (the BUG-002 audit semantics). Java's pruning and SQL both treat it as false, so the core `TableScan` answer depends on whether pages or row groups were pruned. *Recommendation:* a fork card to decide one semantics for the core door; the SQL door already gives Spark's answer.
3. **Q-24b-C: cache defaults.**
   - Metadata cache: 64 MiB.
   - Footer cache: 256 MiB, because indexed wide footers are 1–10 MiB.

   Both are default off in the fork, and RePark chooses the sizes. *Recommendation:* 24a's ICE-CATALOG-CACHE-1 / ICE-FOOTER-CACHE-1 halves pick sizes from the AWS bed once R-3 dispatches resume. Dispatch #2 stopped on an IAM gap.
