# Card F-IDLESS-STRUCT-CHILD-REMAP-1: an id-less Parquet data file with an absent struct child reads a dropped child's value, or a batch of the wrong type (fork card)

**Date:** 2026-10-31. **Filed by:** `claude-haiku-5-5` for the orchestrator, from the RP-63 records round, from the fork ledger of F-STRUCT-EMPTY-CHILD-PANIC-1 (clauses S-11 and S-16) and the orchestrator's probe. **Re-graded 2026-10-31 (RP-63 fix round 1):** from grade B, P2 to grade A, P1, with the RePark route and shape (iii) added, from the RP-63 Opus 5.5 verifier's findings F1 and F3.

**Status:** closed 2026-11-01: fork #379 merged as `ee592dcf`, RePark repinned by RP-64 on branch `chore/rp-64-idless-struct-repin`, awaiting verification and merge. Grade A, P1 (was B, P2) when filed; dispatched on the fork 2026-11-01 (Opus 5.5 builder). The orchestrator's probe (two failing Rust tests) was attached when the unit was chartered; no file path is named here.

**Why:** On a Parquet data file without embedded field ids (the fallback-id path, with or without a name mapping), a struct whose task-schema children are all absent from the file reads wrong values or refuses. The fork's name mapping and fallback-id stamping cover top-level fields only, so a nested struct gets no ids. Three shapes are wrong, all before RP-63:

- (i) a two-leaf file `s<d, e>` with rows `[{d: 1, e: 2}, NULL]`; then add `s.k` and drop `s.d` and `s.e`. The fork's full scan reads `s` validity `[true, false]` and `k = [1, NULL]`: the dropped child's value reads under the new child `k`, which was added after the file was written and must be NULL on every row. Through RePark the same shape answers `(1, {'k': 1})`, silently.
- (ii) a one-leaf file `s<d>`; then add `s.k` and drop `s.d`. In the fork's own test harness the scan returns a record batch whose column is `Struct<d>` under a schema field `Struct<k>`, so `concat_batches` fails with `column types must match schema types`: loud there. Through RePark's door the same shape is silent: `SELECT id, s` answers `[(1, {'k': 1}), (2, None)]` in the same and in a fresh session, and `WHERE s.k = 1` matches row 1. The dropped `d`'s value reads under `k`. Spark answers `[(1, None), (2, None)]`, its NULL collapse, with no wrong value.
- (iii) a one-leaf file `s<d>`; then add `s.k` alone, with `d` not dropped. Through RePark `SELECT *` refuses loud with `DataInvalid` (`failed to cast nested column to Struct(d, k)`, `Incorrect number of arrays for StructArray fields, expected 2 got 1`), in the same and in a fresh session, on both pins. Spark answers `[(1, Row(d=1, k=None)), (2, None)]`.

**Reachability:** RePark's Iceberg writers (INSERT, CTAS, MERGE, UPDATE, `writeTo` and `insertInto`) stamp field ids on every nested child, so these shapes do not come from them. They do come through RePark's own plain frame writer: `df.write.mode("overwrite").parquet(dir)` writes Parquet with no `PARQUET:field_id` at any level, and `CALL <catalog>.system.add_files(...)` admits that file into an Iceberg table. The route needs no other writer, and it is the route that reads shape (ii) silently wrong. The first filing of this card said RePark writes field ids into every Parquet data file it produces; that was false for the frame writer, and this paragraph replaces it.

**Site:** the fork's `nested_projection::build_struct`, whose id-less `PlanNode::Cast` path reads the whole top-level group through `unmapped_group_leaf_indices`; and the top-level-only stamping of `apply_name_mapping_to_arrow_schema` and `add_fallback_field_ids_to_arrow_schema`.

**Fix (proposed):** the id-less struct path projects each child the way the id path does, a child with no leaf in the file reads NULL per row, the struct's validity comes from the file per row (the S-15 rule), and the fallback ids reach nested structs as well as top-level fields. Shape (iii) reads the file's own `d` values with `k` NULL per row.

**Measured (fork ledger S-16, reproduced by the orchestrator at `935cc55c`, `a47b9e01`, `90114dda` and the merge `14a93602`):** shape (i) and shape (ii) above, both with the batch type and values stated. The RePark route, the RePark answers for shapes (i) to (iii) and the same answers on the old pin `935cc55c` were measured by the RP-63 Opus 5.5 verifier on `14a93602` and reproduced by the orchestrator (RP-63 unit ledger, clause C-013). The unit's pins are both shapes end to end on a file written without ids, with and without a name mapping, reading NULL per row with the batch type equal to the schema type, and shape (iii) reading the file's `d` values with `k` NULL per row.

**Label:** a silent wrong value reachable through RePark alone (shape (ii), by the route above). Under section 1 of the label order ([the order](../../wo/ice-v2-label-1/order.md)) a silent value is never a carve-out, so this one cannot be a carve-out. Whether the fork unit runs before the targeted re-audit is the owner's call (not ruled as of 2026-10-31). Label ledger clause C-077 is OPEN for it.

**Retires:** the card when shapes (i) and (ii) read NULL per row with the batch type equal to the schema type, shape (iii) reads the file's `d` values with `k` NULL per row, the pins are green on both doors, and the fork ledger's S-11 and S-16 close by citation; label clause C-077 and unit clause C-013 then close by citation.
