# Card SPARK-DOOR-TEMP-VIEW-TARGET-1: a temporary view's name sends a write to the same-named Iceberg table

**Date:** 2026-10-29. **Filed by:** the second-audit records round (`claude-haiku-5-5`), from the second independent audit of the format-v2 label, finding AUD-006 ([the report](../../../docs/audits/iceberg-v2-label-independent-reaudit-2026-10-29.md), section 3).

**Status:** built at `7984ed39` (2026-10-29, branch `fix/spark-door-temp-view-target-1`, not pushed); verification round 1 pending. Grade A (Opus 5.5 build, with two verifiers: the Opus 5.5 verifier and the standing Muse MAX second verifier, merge gated on the union). The unit ledger is [spark-door-temp-view-target-1-ledger.md](../../ledgers/staging/spark-door-temp-view-target-1-ledger.md).

**Why:** With a temporary view in scope under a one-part name that is also the name of an Iceberg table in the current namespace, the Spark door sends `DELETE`, `UPDATE`, `MERGE INTO`, `INSERT INTO`, `INSERT OVERWRITE` and `TRUNCATE TABLE` to the table, while `SELECT` in the same session reads the view. Spark 4.1.2 refuses every one of those writes, so RePark changes a table by statements that Spark refuses, and the change is silent. The same name resolves to two different objects within one session. The fault predates the shared DML target resolver of #1206: it is identical on the base `321c6095`. Silent data loss by ordinary statements is Critical under the order's section 1 rule.

**Site:** `crates/repark-spark/src/dml_target.rs`. The functions `resolve_dml_target` and `qualify_table_parts` qualify a one-part name by catalog and namespace only and never consult the session's temporary views. The INSERT, INSERT OVERWRITE and TRUNCATE routes resolve the same way without passing through that function.

**Site correction (2026-10-29, builder's hand-back):** the view is lost in the Python facade before the native door, not in the Rust resolver. The facade's write-target expansions in `python/repark/src/repark/spark/session/session_core.py` (INSERT, INSERT OVERWRITE, UPDATE, DELETE and the MERGE INTO target) and in `sql_relations.py` (TRUNCATE) resolved a one-part target with `prefer_temp_view=False`, while the read side took `True`. The Rust `resolve_dml_target` and `qualify_table_parts` are not where the view is lost. The built fix is those five facade edits plus the shared check in `crates/repark-spark/src/view_ddl/temp_write.rs`. The site paragraph above is kept as the audit wrote it.

**Fix:** Every write route (DELETE, UPDATE, MERGE INTO, INSERT, INSERT OVERWRITE and TRUNCATE) consults the session's temporary views before it qualifies the name by catalog and namespace. A one-part name that resolves to a temporary view then refuses the write with Spark's own error class (`EXPECT_TABLE_NOT_VIEW.NO_ALTERNATIVE`, and the unsupported-feature class for UPDATE and MERGE), and the table is unchanged. Each route gets its own pin, shaped as the audit's view-shadow sequence run through the Spark door, comparing the table before and after with the view's own read. The charter confirms the audit's section 4 lead before the build: a `DELETE` through a view over an Iceberg table is accepted by Spark (with no matching rows) and refused by RePark, so the fix must not widen that refusal.

**Built (2026-10-29, product head `7984ed39`):** every route has its pin. `crates/repark-spark/tests/temp_view_write_target.rs` holds 12 tests (8 refusal pins and 4 controls, counted from the file) and `python/repark/tests/writes/test_temp_view_write_target.py` holds 25 cases (11 refusal pins and 14 controls). The write-options precedence and the DELETE class are ruled in the ledger. Verification round 1 and the merge are OPEN. Clauses C-001 to C-006 are PROVEN on the builder's runs; C-007 to C-010 are OPEN.

**Lead resolved (2026-10-29, builder's step 0):** Spark 4.1.2 executes a `DELETE` through a temporary view over an Iceberg table, with matching and with non-matching rows, on copy-on-write and merge-on-read (the table goes from `1,2,3` to `1,3`). RePark refused it before this unit with `TableNotFound` and refuses it now with `EXPECT_TABLE_NOT_VIEW.NO_ALTERNATIVE`, so the refusal is not widened and only its text changed. The executing case is carded as [SPARK-DOOR-DELETE-THROUGH-VIEW-1](spark-door-delete-through-view-1-card-2026-10-29.md) (grade B, P2), not built here.

**Measured (copied from the second audit, reproduced by the orchestrator 2026-10-29):** on RePark, a temporary view and a same-named table in the current namespace: `DELETE FROM` the view-name removes the matching row from the table, `INSERT` and `INSERT OVERWRITE` through the view-name write the table, and `TRUNCATE TABLE` empties it, while `SELECT` from the view-name reads the view. The table reads `[1,3]`, then `[50]`, then `[]` where Spark leaves `[1,2,3]`. On a merge-on-read table, `UPDATE` and `MERGE INTO` through the view-name change the table, where Spark refuses with `UNSUPPORTED_FEATURE.TABLE_OPERATION`, and `DELETE` empties the table while the view still reads its own row. The base `321c6095` gives the same results.

**Retires:** the card when every write route refuses a view-named target as Spark refuses it, each route has its pin, the view-shadow probe matches Spark on both table kinds, and the targeted re-audit of this fix passes. The label ledger's AUD-006 row (`ice-v2-label-1` C-063) then closes by citation.
