# Card F-IDLESS-TOPLEVEL-POSITIONAL-1: on the no-mapping fallback route, a type-changing top-level reorder casts silently where Spark refuses, and a top-level re-added name or a partial mapping reads values Spark does not, reachable through RePark's own name-mapping property (fork card)

**Date:** 2026-11-01. **Filed by:** `claude-haiku-5-5` for the orchestrator, from the RP-64 records round, from the fork ledger of F-IDLESS-STRUCT-CHILD-REMAP-1 (clauses S-20 and S-26). **Rewritten 2026-11-01 (RP-64 fix round 1, verifier F2):** the first filing said no RePark door reaches the route, which was false; the reachability, the diverging shapes and the grade (B, P2, was B, P3) follow the measured answers. **Rewritten again 2026-11-01 (RP-64 fix round 2, verifier F7 and F9):** the first shape is now the silent positional cast on the no-mapping route, where Spark refuses; the nested reorder is recorded as a divergence in RePark's favour. **Rewritten again 2026-11-01 (RP-64 fix round 3, verifier F10 and F11):** the title and the first Why bullet name the silent cast. **Rewritten again 2026-11-01 (RP-64 fix round 4, verifier F12):** the fix is scoped to top-level columns in every clause; every nested by-name read on the no-mapping route is the kept divergence in RePark's favour, since Spark reads no nested child of an id-less file there. The any-depth wording of the round-3 follow-up is superseded.

**Status:** filed; grade B, P2; not dispatched. This is the owner's fork work; the fork is not edited from RePark.

**Why:** On a Parquet data file without embedded field ids, when the table carries no `schema.name-mapping.default` (the fallback-id route), the top-level rule (match by name and position, else `position + 1`) reads by position. Measured on the fork at `14a93602` and before, and through RePark's Spark door on both pins, 2026-11-01:

- A top-level reorder that changes a type casts silently on RePark where Spark refuses: the fallback rule casts the neighbour's column into the field's type, so a cast that fails reads NULL and a cast that succeeds reads a wrong value. The same answer comes back in the same and in a fresh session, on `14a93602`, `ee592dcf` and `56ff5545`, through the UNSET route. Table `(a INT, b STRING)` over a file `(b STRING, a INT)`, rows `('p', 1), ('q', 2)`, reads `[(None, '1'), (None, '2')]` on RePark, and `WHERE a = 1` and `WHERE b = 'p'` count 0; Spark 4.1.2 raises `ClassCastException` (`SELECT b` alone raises `UnsupportedOperationException`). The same shape with rows `('7', 1), ('8', 2)` reads `[(7, '1'), (8, '2')]` on RePark; Spark raises `ClassCastException`. Table `(a INT, b BIGINT)` over `(b BIGINT, a INT)`, rows `(40, 1), (30, 2)`, reads `[(None, 1), (None, 2)]` on RePark; Spark raises `ClassCastException` on `SELECT a, b` and reads `[(1,), (2,)]` on `SELECT b`. Table `(a INT, b DATE)` over `(b DATE, a INT)`, row `(2020-01-02, 1)`, reads `[(18263, date(1970, 1, 2))]` on RePark, a date read as an int; Spark raises `ClassCastException`. Only a struct-for-scalar swap is loud on RePark (`Casting from Struct(...) to Int32 not supported`); Spark raises `IllegalArgumentException: Not a struct type: int`.
- table `(x, a, b)`, id-less file `(a, b)` with `a = [1, 2]` and `b = [40, 30]`: reads `x = [1, 2]`, `a = [40, 30]`, `b = NULL`. Spark 4.1.2 gives the same positional answer (Java's fallback assigns ids by position), so this shape is Spark-equal and is recorded, not a divergence. Table `(a, b)` over a file `(b, a)` of the same types: the values swap on both engines (Spark-equal, Java's rule).
- a struct child or a top-level column dropped and then re-added by the same name: RePark reads the dropped field's old values (`drop s.b`, then `add s.b`, reads `{a: 1, b: 2}`; `drop c`, then `add c`, reads `c = 5`), where Spark reads NULL (`(1, None, None)`). A by-name rule without schema history cannot tell a re-added field from the original (fork S-26). This diverges from Spark: its top-level part is in the fix, and its nested part falls under the nested rule below.
- a `SET TBLPROPERTIES` of a mapping that names only `zz`, over the file `(a, c)`: RePark reads `(1, 2)`, where Spark reads `(None, None)`. This diverges from Spark.
- Spark's nested rule on this route (after `UNSET`, with no reorder and no evolution): Spark reads no nested child's value from an id-less file at all, an optional struct group reading `s` NULL (`[(1, None), (2, None)]` over a file in the same child order) and a required group reading a non-null `Row(d=None, e=None)` (`[(1, Row(d=None, e=None)), (2, Row(d=None, e=None))]`, `s IS NULL` false), and after `UNSET`, `DROP s.b` then `ADD s.b` reads `[(1, None)]`; RePark reads the file's data by name in each of these (`[(1, {'d': 1, 'e': 10}), (2, {'d': 2, 'e': 20})]` and `[(1, {'a': 1, 'b': 2})]`), a divergence in RePark's favour that is kept outside the fix.

**Reachability:** through RePark's own door. `ALTER TABLE t UNSET TBLPROPERTIES ('schema.name-mapping.default')` is accepted on the Spark door after `add_files` and leaves the table with no mapping; a `SET TBLPROPERTIES` of a mapping that names other columns gives the partial-mapping shape. RePark does not refuse the UNSET, because Spark accepts it. The route is also reached by a table registered from foreign metadata with no mapping. `add_files` itself installs a mapping, so the id-less file admitted by it does not take this route. The RP-64 pins do not run this route.

**Site:** the fork's no-mapping fallback route for id-less files, the top-level name-and-position rule with its `position + 1` fallback. The fork ledger names the functions.

**Fix (proposed):** the no-mapping route refuses a TOP-LEVEL file column whose type is not promotable to the positional field's type, as Spark does; answers as Spark's positional fallback does for top-level columns, including NULL for a re-added TOP-LEVEL name and for the partial-mapping shape, as Spark does (today the fork reads the dropped field's old value for a re-added top-level name and the file's current values by name under a partial mapping). Every nested by-name read on the no-mapping route is the kept divergence in RePark's favour and is not part of this fix. The positional read and the same-type reorder follow Java's rule and are Spark-equal, as measured.

**Measured:** fork ledger S-20 and S-26 (the probes of the fork's round-3 verifier, V3-F2, and the fork's own builder), at `14a93602` or earlier; the RP-64 Opus 5.5 verifier's F2 oracle of 2026-11-01 (its shapes f1, f3, f4 and f5, on both pins, with Spark's answers); and its round-2 oracle of the same date (F7 and F9: shapes f2, f4b, f4b2, f4c, f4d and f4e, with Spark's answers; the F7 shapes on `14a93602`, `ee592dcf` and `56ff5545`), and its round-4 oracle of the same date (F12: the nested reads in the last bullet under Why, copied from the unit ledger's Verifier round 4 section). The nested reorder (shape f2, `s<d, e>` over the file `s<e, d>` on the UNSET route) reads `{d: 1, e: 10}` on RePark, by name and right against the data, where Spark reads `s` NULL (`[(1, None), (2, None)]`); that is a divergence in RePark's favour, kept, not a defect.

**Retires:** the card leaves when the top-level unpromotable-type read refuses naming the column and both types, and the top-level re-added name and the top-level partial-mapping shape read NULL as Spark does, with fork ledger S-20 and S-26 closing by citation.
