# Unit ledger — ICE-RDF-SORT-PARSE-1 · CALL rewrite_data_files strategy and sort_order (IPI-43)

**Date:** 2026-09-20 (round 1 built the code and pins; round 2 files this ledger) · **Branch:** `fix/ipi-43-rdf-sort-zorder` · **Base:** `d89f8130` · **Model:** muse-spark-1.3-contributor · **Policy:** [../../../AGENTS.md](../../../AGENTS.md).
**Path:** STANDARD. **risk_tier: standard.**

**Retires:** this ledger moves to `../completed/` when the unit's last commit lands.

**Why now.** `strategy => 'sort'` and `sort_order => …` on `CALL … rewrite_data_files` were blanket refusals. They now parse and route onto the fork's `RewriteStrategy::{SortByTableOrder, Sort, ZOrder}`, which the pinned fork rev already carries (round-1 commit `20ac235d`). The three inventory cells this unit closes — `P-RDF-SORT`, `P-RDF-SORT-TABLE-ORDER`, `P-RDF-ZORDER` — record the same output row, the same `files_after`, the same rows and the same metadata on Spark, so a rewriter that ignored `strategy` and `sort_order` and bin-packed would turn all three EQUAL while doing nothing. The pins therefore read each rewritten data file straight out of parquet and assert the row order inside it, against the 7-cell Spark oracle the recorder beside them measured on live Spark (`ice_rdf_sort_parse_1_spark_oracle.json`).

**Not in this unit:** the `branch` argument (the fork builder has no branch parameter, so accepting it would ship a silently ignored argument; IPI-31 owns it); non-`zorder` transform sort terms (a registered CALL-door refusal, `RDF-SORT-TRANSFORM-1`, not a parse failure); `STATUS.md`; version numbers.
