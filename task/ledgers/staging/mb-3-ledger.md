## Decisions

- **D-1 (2026-10-07). `register` is async and takes the session.** The sketch's
  `StreamingQueryManager::register(&self, spec)` is synchronous and `QueryHandle::id()` returns a
  `QueryId`, but the id is `QueryId::derive(sink uuid, queryName)` (sketch §3.1), and the uuid
  lives in the sink's metadata, which only an async catalog load reads. `register` therefore
  loads the sink, and takes `&Session` because the manager rides inside the session's config and
  must not hold the session (that would be a reference cycle through the config extension).
  Registering still does not start the query (CC-1 rule 1); MB-4's `toTable` / `start` call
  both, as Spark's do.
- **D-2 (2026-10-07, OQ-2a-2, acted on the recorded lean under the North Star's act-on-the-default
  rule; open for the owner and the Frontier to overrule).**
  - **The question:** where the epoch stamp goes when a `foreachBatch` body writes the sink more
    than once.
  - **Flink:** a two-phase-commit sink, so the stamp is atomic with every write.
  - **Spark:** `foreachBatch` is at-least-once; a multi-write body replays (W4, W6).
  - **The default acted on:** the `foreachBatch` door stamps once, through a trailing
    `commit_stamp_only` after the body returns; the body's data commits stay unstamped
    (at-least-once on multi-write bodies, Spark's contract), and the `toTable` door keeps its single
    stamped commit (exactly-once for a single driver; qualifier added 2026-10-07, fold 1: the
    guarantee is not claimed against a racing driver on the same sink while C-002 is open). The cost is a second catalog commit per `foreachBatch` batch
    (North Star §5 Performance: this is the reason shown). Sketch Q9's "one stamped sink commit per
    batch, a second refuses" and `RecoveryRequired(UnstampedSinkCommit)` for an unstamped head no
    longer apply on this door; MBE-13's `SinkCommittedTwice` stays reachable only through the
    stamp-only path, which the driver calls once.
- **D-3 (2026-10-07, MB-2a D-10).** "The batch's session config" is read as a private
  `SessionContext` built per batch from a clone of the session state, and the token is installed
  there, never in the user's shared session config. A token in the shared config would let any
  concurrent write to the sink on the same session claim the batch stamp, which is the foreign-writer
  hazard MB-2a's fold 1 closed (North Star §8 case 3). Under D-2 only the `toTable` door writes
  through that batch session; the `foreachBatch` body runs on the user's session without the token,
  and the trailing stamp passes the token directly. The batch session is dropped at the end of the
  batch, which removes the key.
- **D-4 (2026-10-07). `time_travel/microbatch_source.rs` gains four accessors.** MB-1's source
  plans to the current head. `availableNow` needs Spark's fixed end (`prepareForTriggerAvailableNow`,
  MB-1 D-5), so the source gains `available_now_target` (the uncapped walk's end) and
  `next_batch_until` (a capped window cut at the end by ancestry and position), plus `table_uuid`,
  `table_identifier` and `name` for the resume check. The existing paths are unchanged and every MB-1
  pin stays green.
- **D-5 (2026-10-07). `StreamSpec` gains `polling_delay`; a zero `stop_timeout` waits forever.**
  The sketch's `StreamSpec` names no field for `spark.sql.streaming.pollingDelay` (R-15, Spark's
  10 ms default, kept). `stop_timeout: Some(0)` is read as Spark's `stopTimeout=0`, wait forever
  (sketch Q7 rule 2). Pinned 2026-10-07 (fold 1, C-018).
- **D-6 (2026-10-07, R-12 / OQ-5). The local-catalog refusal and the test seam.** A sink catalog is
  local when the session registered it with `LocationPolicy::TempFallbackAllowed`, the policy only
  the memory (and `hadoop`) catalog gets (`session/memory_catalog.rs`). The Rust pins start below the
  check through `QueryHandle::start_below_catalog_check`, compiled only under `cfg(test)`; MB-4 owns
  the private `_native` seam its Python cells need.
- **D-7 (2026-10-07, observed for MB-4).** `BatchBody::run` returns a `Send` future (the sketch's
  `BoxFuture`), and the driver task is spawned, so a body cannot await `Session::sql`, whose future is
  not `Send` (`session/write_options.rs`, the dialect's boxed future). The Rust pins write the sink
  through `stage_overwrite_files_with` and `commit_append_with_summary` with the session's resolved
  write options instead. MB-4's Python body runs the callable under the GIL inside the batch and must
  not hold a non-`Send` future across an await.
- **D-8 (2026-10-07). Slices 2 and 3 land in one commit.** The `Door` enum carries the
  `foreachBatch` body from `register` on, so a slice-2 commit without the door would either warn
  (a dead field, red under `-D warnings`) or ship a placeholder refusal. The two slices keep separate
  clauses (C-004, C-005) and separate mutations.
- **D-9 (2026-10-07). Progress details the sketch leaves open.** `StatusMessage::Initializing`
  and `ProcessingNewData` render `Initializing sources` and `Processing new data` until DM-2
  records Spark's words. `StreamSpec` gains `recent_progress_limit` (Spark's
  `numRecentProgressUpdates`, default 100). The idle-progress throttle is Spark's
  `noDataProgressEventInterval` default (10 s), unmeasured; the draining-trigger rule is measured
  (MB0b-R14, R15). `sink.numOutputRows` renders `-1` (Spark's `SinkProgress` default) when the
  door counts no rows, which is the `foreachBatch` door; the `foreachBatch` value is unmeasured.
  Added 2026-10-07 (fold 1): a `recent_progress_limit` of `0` is clamped to `1`, so the ring
  keeps the newest progress. Spark 4.1.2 with `numRecentProgressUpdates=0` fails the query
  after its first batch (`STREAM_FAILED`, `NoSuchElementException: empty collection`, cell
  MB3-G1); that is a crash in its progress buffer, not a contract, so the clamp stays and the
  difference is registry row `MB-3-PROGRESS-RETENTION-0` (C-018).
- **D-10 (2026-10-07). `streaming_frame` is async and `StreamSpec::plan` is optional.** The
  placeholder needs the source's read schema, which only an async catalog load reads, so
  `streaming_frame` is `async` where the sketch writes it synchronous. `StreamSpec.plan` is
  `Option<PlanTemplate>`: `None` runs the source frame unchanged (the Rust pins and any caller
  without a transformation), `Some` must read the spec's source. Two further refusals beyond
  the sketch's list: a window function (Spark refuses non-time windows on a stream) and more than
  one streaming source in one query (MB-5's vector form). The stateful check runs before the
  source count, so a stream-stream self-join names the join.
- **D-11 (2026-10-07, fold 1, ruling F3). The session's end stops its queries.**
  - **The question:** what happens to a running query when its session goes away.
  - **Spark:** stopping the session stops its queries.
  - **The contract:** an explicit session stop is `StreamingQueryManager::stop_all`; it stops
    every active query of the session and waits for each as `stop()` does (`ReparkSession` has
    no stop method in Rust today; MB-4's `spark.stop()` calls it). Dropping the last handle
    to the session without a stop signals every running query to stop and does not wait; each
    ends `Stopped` after its in-flight batch, and the task and its catalog handles are
    released. A query handle the caller still holds keeps the sink's catalog handle until it
    is dropped.
  - **How the drop is seen:** through a `Weak` to the session's catalog registry
    (`Session::catalogs`, an `Arc` held only by the session's handles), read at every stop
    check and polled every 100 ms inside the trigger wait and the scope wait. The ruling's
    example, the manager's `Drop`, cannot fire while a driver task runs: `MicroBatchSource`
    (`time_travel/microbatch_source.rs`, outside the fold's files) owns a `SessionContext`
    clone, the context owns the config, and the config owns the manager. `session.rs` sits
    exactly at the 1000-line ceiling, so a hook there would need a size exception; it is not
    edited. Replacing the poll with the manager's `Drop` needs the source to hold a weak
    context, which is the hand-back's question Q1.
  - **Round 2 (2026-10-08, Q1 ruled YES), replacing the paragraph above:** the source, the
    driver task and the pending work hold a weak session state, the manager's `Drop` sends
    the stop, and the poll is gone. The poll is not kept, for this reason: the one case the
    signal misses is a state snapshot that outlives every session handle (a `DataFrame` the
    caller still holds carries the config, and so the manager). There the `Weak` fallback
    ends the query at its next stop check, which is the top of its next trigger, before any
    planning or batch; a query mid-interval lingers as an idle task until then, and the
    snapshot that keeps it pins the catalogs anyway. No batch starts after the session's
    handles are gone in either case. A planning error after the session ended is reported as
    a stop, and the `toTable` door stops before its write when the state is gone (C-021).
- **D-12 (2026-10-07, fold 1, ruling F2). One lifecycle lock, and its order.** `Pending` moved
  from its own mutex into `Lifecycle`. `start` holds the query's lifecycle while the manager
  admits it and until the task is spawned and its `AbortHandle` stored; `stop` on a registered
  query concludes under the same lock. Order: own lifecycle, then the registry, then the
  lifecycle of a query already in the registry. A query enters the registry only inside its
  own `start`, so no path holds a registered query's lifecycle while it takes the registry.
- **D-13 (2026-10-07, fold 1, ruling F1). A panic is reported as `BatchFailed`.** The
  taxonomy (`repark-iceberg/src/microbatch/error.rs`) is outside the fold's files and the
  ruling asks for "exactly as a body error does", so the cause is
  `the driver task panicked: <message>`, credential-masked, under the in-flight epoch, or the
  next epoch when the panic came before a batch began. The batch's `BatchScopeGuard` drops
  during the unwind, so the sink's scope is released. **Round 2 (2026-10-08):** the panic now
  has its own variant, `DriverPanicked { epoch, message }`, with the panic's message
  credential-masked (C-020).
- **D-14 (2026-10-07, fold 1, ruling F6). The scope wait, and `SinkBusy` at start.** `start`
  compares the sink's table uuid against the session's active queries, after the same-id
  check, so a second run of one query still reports the id. The batch enters its scope
  before the resume-point check and reloads the sink after each wait, because the query
  that held the scope has committed to the sink meanwhile. `StreamSpec` gains
  `catalog_timeout` for the wait's bound.
- **D-15 (2026-10-07, fold 1). Edits outside the microbatch directory.** The MBE-6 row lives
  in the design sketch (`task/wo/microbatch/mb-design-2026-10-06.md` §4), so the fold's
  instruction to extend that row is carried out there, dated, and nowhere else in that file.
  The fold's four Spark cells are a new recorder, `mb3_fold_oracle.py`, with its own JSON and
  checksum, so the MB-0 recording stays byte-identical.
- **D-16 (2026-10-08, round 2, Q2). What the catalog timeout wraps.**
  - A read is bounded as one call of the source or one sink load. The source's catalog load
    lives inside `MicroBatchSource`, whose edit in this round is the weak state only, so the
    bound on `initial_offset`, `available_now_target` and `next_batch` also covers that call's
    manifest reads. An uncapped walk over a long history (`Once`, the `availableNow` end) that
    takes longer than the timeout fails `CatalogTimeout`; the caller raises
    `repark.cdc.catalog-timeout`. Moving the bound onto the load alone is an edit inside the
    source.
  - A commit that times out is dropped mid-flight, so its outcome is unknown by definition:
    it goes to `resolve_unknown_outcome` with no operation id (the id is minted inside the
    commit), which matches the landed snapshot by its record. The walk is bounded by the same
    timeout and reports `RecoveryRequired(CommitOutcomeUnknown)` when it stalls too.
  - `register` and `stop`'s re-read after a stop timeout are bounded too. `stop` falls back to
    the durable record it already knows.
  - The key itself is not parsed here: `StreamSpec.catalog_timeout` carries the value, as
    `stop_timeout` and `polling_delay` carry theirs, and MB-4 maps the option onto it.
  - Registry row `MB-3-SINK-BUSY-1` (`docs/spark-sql-iceberg-parity.md`) quoted `SinkBusy`'s
    old text, so its quotation is updated with the text; nothing else in that file moves.
