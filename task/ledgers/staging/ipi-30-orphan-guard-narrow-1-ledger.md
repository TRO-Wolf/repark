# Unit ledger — IPI-30-ORPHAN-GUARD-NARROW-1 · remove_orphan_files sweeps a fallback table's own directory and accepts file_list_view (lane xo55-orph2)

**Date:** 2026-09-22 · **Branch:** `fix/ipi-30-orphan-guard-narrow` · **Base:** `85011ea0` · **Model:** claude-opus-5-5 · **Policy:** [../../../AGENTS.md](../../../AGENTS.md).
**Path:** STANDARD. **risk_tier: high** (the procedure deletes files; the change widens what it may sweep).

**Retires:** this ledger moves to `../completed/` when the unit's last commit lands.

**Why now.** On `85011ea0` every memory-catalog table created in a namespace without a `location` refused `remove_orphan_files`, because the table sits under the shared CTAS fallback root `<warehouse>/repark_ctas/<catalog>/<ns>/<table>` and the guard refused anything *in* that root. Spark 4.1.2 sweeps the same shape (scoreboard cells P-ORPHAN-DEFAULT … -STREAM-RESULTS, nine refuse on RePark). Owner ruling Q-55-6 "(A) NARROWED" (claims file, 2026-09-22) keeps only the safety property "never sweep a directory that holds another table's files", which the orchestrating session fixed as the three refusals (a), (b), (c) below; a scan path strictly inside another table's directory is none of them. The same round accepts `file_list_view` (cell P-ORPHAN-FILE-LIST-VIEW), which refused `NotImplemented`.

**The guard as ruled.** The scan path is the `location` argument, or the table location when it is absent. It refuses only when the scan path (a) is `<root>/repark_ctas` or `<root>/repark_ansi_ctas` after the lexical and `file:` / `file://` / `file:///` normalisation, (b) is a parent of that root, or (c) equals or contains the location of another table in the same catalog, found by walking every namespace and table through the catalog API, excluding the swept table. (a) and (b) keep the old refusal text; (c) names the other table. The guard fires only on a `TempFallbackAllowed` catalog, the same scope the old guard had.

**Not in this unit:** Cargo.toml / Cargo.lock and the fork (the view path reuses the fork's public `DeleteReachableFiles` collector for the referenced set); `ctas.rs` (Q-55-7); the scoreboard harness; `refuse_service_managed_orphan_sweep`; STATUS.md; the 24-hour `older_than` floor.

## Design notes (why, not what)

- The referenced set for the view path is the fork's `DeleteReachableFiles` walk with a collecting `delete_with`, so no Cargo or fork edit is needed. The fork's module doc says that walk covers every snapshot's manifest list, every manifest, every entry including DELETED tombstones, the whole metadata log, the version hint and the statistics files. RePark's own pins show only that the live data file, in a bare or `file:` spelling, is subtracted (C-005).
- The view join follows the shape of Java `compareToFileList`: candidates are the rows with a non-null `last_modified < older_than` whose path lies under the scan location (C-012, C-013), joined on the URI path with the `equal_schemes` / `equal_authorities` maps and the `prefix_mismatch_mode` classification (C-011, C-015). The containment test is component-wise after the guard's normalisation, so a `..` escape is not a candidate (C-013). Spark's answer for an out-of-scope path is unmeasured, and no Java source was read to compare the containment test.
- `gc.enabled = false`, or an unparsable value, refuses the view path with the fork's own error built the same way, because the view path does not run the fork action that owns that gate; both doors answer one string (C-014).
- The procedure body moved from `call.rs` to `call/remove_orphan_files.rs`, with the view join in `call/orphan_file_list.rs`, so `call.rs` stays well under its size ceiling. Moved code sheds its comments.
