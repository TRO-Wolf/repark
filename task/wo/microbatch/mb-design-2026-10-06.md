## 1. W8 — the contradiction MB-0 reported, ruled

MB0-W8 records Spark's answer. `writeStream.format("iceberg")…toTable(sink)` with no `checkpointLocation`
fails at `toTable()`, synchronously, before any batch runs. It raises `AnalysisException`, class
`_LEGACY_ERROR_TEMP_1298`, SQLSTATE null, with the text `checkpointLocation must be specified either through
option("checkpointLocation", ...) or SparkSession.conf.set("spark.sql.streaming.checkpointLocation", ...).`,
and `spark.sql.streaming.checkpointLocation` is unset.

O-1 and D-1 rule where state lives: no checkpoint directory for an Iceberg sink. NS §6 rules the surface:
the option is accepted and recorded, never read, unless Spark refuses. Spark refuses the *omission*, not the
*combination*. Under §2 the surface follows Spark and the state follows O-1. The two do not collide, because
requiring a string is not the same as using a directory.

**Ruling (record R-1).**
- An Iceberg-sink query with neither the option nor the session conf refuses at `toTable()` / `start()`. It
  copies Spark's class, its null SQLSTATE and its text verbatim.
- With either one present, the value is held on the query handle and nothing more. It is never created,
  listed, read or written, and never rendered.
- No ruled row changes: O-1 still holds, since no directory exists, and D-1 left the accept-or-refuse
  question to the oracle. This is therefore not a §8 halt.
- Flink differs: it does not require a checkpoint location for a sink. That difference goes to the owner as
  OQ-1, without halting.
- The `foreachBatch` door's omission was not recorded (W8 used `toTable`). It takes the same refusal until
  the deferred cell DM-1 says otherwise.

## 2. Q1…Q11, ruled

**Q1 · `checkpointLocation` on an Iceberg sink (MB0-W8; W1…W7 all pass one).** The option is accepted and
never read. Its omission is refused with Spark's `_LEGACY_ERROR_TEMP_1298`, verbatim, at query start (§1,
R-1). Every W-cell that passes the option succeeds, so passing it is never an error.

The value names no store. Pointing a restarted query at a new location does not reset it, because the
query's identity comes from the sink (§3.1). That is a dated difference from Spark, where a new checkpoint
starts a new query (R-6). Registry row MBE-5.

**Q2 · the `Once` trigger (MB0-T1).** Supported. `trigger(once=True)` runs one batch over everything
available at start and then stops (`isActive` false). It **ignores** both read caps: with
`streaming-max-files-per-micro-batch=1`, T1 still records one batch of 3 rows across two snapshots.

D-3's two triggers stand, and `Once` is a third `Trigger` arm with `WindowLimit::Unbounded` (§3.3, §3.5).
That T1 runs uncapped conflicts with NS-7's caps. It is recorded as R-2 and goes to the owner as OQ-2. There
is no error class.

**Q3 · `complete` output mode (MB0-W3).** Refused in 1.7. Spark supports it: each batch commits an
`overwrite` snapshot holding the whole aggregate (`k0=1, k1=2`, then `k0=2, k1=3`). It does so through a
streaming aggregation whose state sits in the checkpoint's state store. That is a second store, which NS-2
and O-3 forbid, and no slice builds a stateless equivalent.

The refusal fires at query start, before any batch. It uses the SES-DECL shape, `PySparkNotImplementedError`
with `NOT_IMPLEMENTED` and `{"feature": "outputMode(complete)"}`, under registry row MBE-6. The same row
refuses `update` mode and any stateful operator in the plan (aggregate, stream–stream join,
`dropDuplicates`, sort, global limit).

The fix the refusal names: use `foreachBatch` with a batch aggregate over the source `VERSION AS OF` the
batch end, then overwrite. A stateless recompute-at-end card, `MB-COMPLETE`, is reserved by name (R-3, OQ-3).

**Q4 · a `replace` snapshot inside a window (MB0-R8, MB0-R9).** Skipped silently, and the next append
streams. R8 has no options and R9 sets `streaming-skip-overwrite-snapshots=true`; both record the
`rewrite_data_files` snapshot not re-streamed and row 4 streamed in batch 1.

The fork already does this: `NonAppendPolicy::refuses` never refuses `Replace`
(`fork:crates/iceberg/src/scan/incremental/window.rs:31`), and the append filter drops it. This meets O-5:
O-5 rules delete and overwrite, and a `replace` rewrites existing rows without adding any, so skipping it
neither loses nor duplicates a row. Compaction on Bronze stays an allowed maintenance procedure. There is no
error class.

**Q5 · Spark-checkpoint migration — ruled by the owner (2026-10-05), restated.** A query always starts from
the sink's offsets, and a Spark checkpoint is never parsed. Migration is a one-time explicit start-snapshot
option on the first run, documented as a dated difference row.

The shape that is never parsed is MB0-R13: `offsets/N` holds three lines (`v1`, the batch metadata, then
`{"version":1,"snapshot_id":…,"position":…,"scan_all_files":false}`), plus `commits/N`, `metadata` and
`sources/0/offsets/0`. The option is `repark.cdc.start-after-snapshot-id=<id>`, which is exclusive: `<id>`
and its ancestors count as consumed. It applies only when the sink holds no offsets for the query.

The migration recipe in the docs: drain the Spark query with `availableNow` so that its last *committed*
offset is a snapshot boundary. Take `snapshot_id` from the third line of the last `offsets/N` that has a
matching `commits/N`, and pass it. Spark's `stream-from-timestamp` (R10) is the other first-run start.
Registry row MBE-12; records R-7 and R-13.

**Q6 · summary keys, the property key, and the offset encoding (MB0-W7, W1, W2, R11…R13, T3).**

- **The summary.** Every micro-batch commit carries six keys:
  - `repark.cdc.format-version` = `1`;
  - `repark.cdc.query-id`;
  - `repark.cdc.run-id`;
  - `repark.cdc.epoch`;
  - `repark.cdc.generation`;
  - `repark.cdc.offsets`, the batch's **end** offsets as a JSON array.

  The `toTable` door also writes W7's `spark.sql.streaming.queryId` (the same UUID) and
  `spark.sql.streaming.epochId` (the same epoch), because Iceberg's own Spark sink stamps them (W1, W2 and
  W7; authority rank 3; record R-5). The `foreachBatch` door does not write them, because Spark's
  `foreachBatch` writes do not (W4). Fanout changes no key (W1 and W2 carry the same set).
- **The property.** `repark.cdc.offsets.<query-id>` holds
  `{"format-version":1,"run-id":"…","epoch":E,"generation":G,"inputs":[…]}`.
- **One offset.** An input's offset is `{"table":"<ns>.<name>","table-uuid":"<uuid>","snapshot-id":<i64>,"position":<u64>}`.
  `table` is informational and never compared; the uuid is the identity.
- **The vector.** The array is sorted by `table-uuid`. A single input is the length-1 vector: there is one
  format and no special case.
- **Position.** Following R13 and T3, `position` counts the added data files of `snapshot-id` already
  consumed. In R13 one 3-file snapshot gives positions 1, 2, 3, and in T3 one 1-file snapshot gives position 1.
  `(S, p)` therefore means "all snapshots before `S` in the ancestry, plus files `[0, p)` of `S`, are
  consumed".
- **File order inside a snapshot.** Files are sorted by data-file path, so a replay is identical on any
  machine (NS-3). Spark's order is the manifest order, so positions are not interchangeable with Spark's.
  That does not matter, because Spark offsets are never read (Q5).
- **Progress rendering.** `lastProgress.sources[i].startOffset` / `endOffset` render Spark's exact Iceberg
  JSON, `{"version":1,"snapshot_id":…,"position":…,"scan_all_files":false}`, as T3 records.

**Q7 · `StreamingQuery` states, progress, `awaitTermination` / `stop` (MB0-T3, T2, R2, W6) under CC-1.**

- **States.** The states are NS-16's enum: `Registered`, `Running`, `Draining`, `Stopped`, `Failed`,
  `RecoveryRequired`.
  - `isActive` is true in `Running` and `Draining` (T3: true before `stop`, false after; T2: false after
    `availableNow` drains).
  - `status` renders `{"message","isDataAvailable","isTriggerActive"}`. Between triggers it is
    `"Waiting for next trigger"` and after a stop `"Stopped"`, both exact from T3. Other messages are
    deferred cell DM-2.
- **`lastProgress`.** It carries T3's field set (§3.6).
  - `startOffset` is null on the first batch.
  - `sink.description` is the sink identifier.
  - `sources[].description` is a RePark rendering. Spark's is a volatile object identity.
  - `durationMs.walCommit` and `durationMs.commitOffsets` are `0`, because there is no checkpoint log; the
    Iceberg commit is timed inside `addBatch`, as in Spark (R-16).
  - A trigger that finds no data reports `numInputRows: 0` with the next `batchId` and commits nothing. W5's
    third run shows this: `batchId 2`, `numInputRows 0`, no new offsets or commits entry.
- **`awaitTermination()` and `stop()`.**
  - `awaitTermination()` returns `None` when the query stops cleanly (T2, T3).
  - `awaitTermination(timeout)` returns `True` once the query has terminated (T3), and `False` on timeout.
  - A failed query raises `StreamingQueryException`, `STREAM_FAILED`, SQLSTATE `XXKST`, with Spark's
    `Query [id = …, runId = …] terminated with exception: …` head (R2, R5, W6).
  - `stop()` returns `None` (T3).
- **CC-1's four rules.**
  1. `register` builds the handle and `start` runs it. The Python `toTable` / `start` do both, as Spark's
     do.
  2. `stop()` waits for the in-flight batch, up to `spark.sql.streaming.stopTimeout` (`0` waits forever),
     and its Rust return is `ShutdownOutcome` carrying the durable `SinkRecord`. This differs from Spark,
     whose `stop` interrupts the batch; CC-1 is ruled, so it wins (R-10).
  3. A stop timeout or an unresolved commit outcome yields `RecoveryRequired` and raises
     `RecoveryRequiredException` from `stop()` / `awaitTermination()`.
  4. Dropping the Python object does not stop the query; `spark.streams` and `spark.stop()` do.

**Q8 · the same-key property race (fork #366, merged `267370b7`).** The fork's pin
`retried_commit_overwrites_a_concurrent_same_key_property_without_notice`
(`fork:crates/iceberg/src/transaction/offset_property_retry_tests.rs:287`) proves that a retried commit
clobbers a racer's property silently. No `TableRequirement` asserts a property value, so **the protection
lives RePark-side, in MB-2c (CC-9)**. It closes the race by never letting an offset write rebase.

- **Every offset write rides a pinned commit.** The property is set in the same `Transaction` as a snapshot
  that is fenced to the base `H` the epoch check read.
- **The MERGE door.** The copy-on-write arm passes `validate_from_snapshot(H)` with
  `validate_no_conflicting_data()` (`crates/repark-iceberg/src/write/merge/snapshot_commit.rs:174`–`:187`).
  The merge-on-read arm's `row_delta` validates from the transaction's starting snapshot, which survives the
  re-base (`fork:crates/iceberg/src/transaction/mod.rs:139`, `:527`–`:529`). The isolation level must be
  serializable: a stamped MERGE into a sink with `write.merge.isolation-level=snapshot` refuses (MBE-15).
- **The append door (`toTable`, and `writeTo(sink).append()` inside `foreachBatch`).** `merge_append` /
  `fast_append` validate nothing and always re-base (`fork:…/transaction/mod.rs:506`–`:515`; FastAppend
  `fork:…/transaction/append.rs:108`–`:131`). `row_delta` cannot stand in for them: a data-only row delta is
  `Overwrite` at this pin (`fork:…/transaction/row_delta.rs:773`–`:786`), and a downstream stream would
  refuse it (R2).
- **The trigger that picks the append-door branch.**
  - **Branch A, fork-free:** the same transaction carries an empty `overwrite_files()` with only
    `validate_from_snapshot(H)` and `validate_no_conflicting_data()` beside the append. MB-2c measures it
    first (DM-6). It is accepted only if the commit still holds exactly one snapshot, with operation
    `append`.
  - **Branch B:** otherwise the fork ask `F-APPEND-PIN-BASE-1` (§7, OQ-4) adds
    `validate_from_snapshot(id)` plus `validate_no_concurrent_data()` to the two append actions, default
    off. Its RP-N pin merges before MB-2c, as the F-COMMIT pin does.
  - Until one branch is green, harness pin 3 stays red on the append door, and MB-2c halts under its own
    halt rule 2.
- **Resume reads the summary as the authority and the property as its one-read mirror.** A disagreement is
  `RecoveryRequired(OffsetMismatch)`, never a guess.

**Q9 · the `foreachBatch` contract (MB0-W4, R1, W5, W6).**

- **The signature** is Spark's: `func(batch_df: DataFrame, batch_id: int) -> None`. `batch_id` is the epoch.
  It starts at 0 and continues from the sink across restarts (W5: 0, 1, 2), and a replay sees the same
  `batch_id` (W6: batch 1 re-ran as batch 1).
- **The frame** has the source schema (R1).
- **A failure.** A callable that raises fails the query: `STREAM_FAILED`, the Python error in the cause
  chain (W6), and no retry inside the query (NS-8). Restart replays the same epoch.
- **Exactly-once covers the declared sink only.** The declaration is the RePark-owned writer option
  `repark.cdc.sink=<table>`. Without it the query refuses at start (MBE-10, R-9), because the offsets would
  have nowhere to live (NS-1, NS-2).
- **What the callable observes.** Inside the callable, a `BatchScope` (§3.4) stamps and fences the batch's
  commit to that sink. It applies at the three named commit sites: `writeTo(sink).append()` and an
  `INSERT INTO` that reach `commit_append_with_summary`
  (`crates/repark-iceberg/src/write/write_options.rs:433`), and `MERGE INTO sink` on both arms
  (`snapshot_commit.rs:174`, `:408`).
  - One stamped sink commit is allowed per batch. A second one refuses (MBE-13).
  - If the callable returned without a sink commit, the runtime commits a stamp-only snapshot (R-18,
    DM-5).
  - If the sink head moved without the stamp, the commit went through an unstamped path, and the query ends
    `RecoveryRequired(UnstampedSinkCommit)`.
  - Writes to any other table are side outputs, at-least-once, which is Spark's `foreachBatch` contract
    (W4: the batch writes carry no streaming keys).
- **Replays across a cap change.** The rows of a replayed epoch are a function of the sink offset and the
  read caps. Changing a cap between a failure and the restart changes the replayed batch, whereas Spark
  replays its logged end offset (R-11).

**Q10 · maintenance hooks — ruled by the owner (2026-10-05), restated.** The slices carry no maintenance
hooks. The driver never runs expiry or compaction implicitly. The only thing shipped is the guard that
offsets are read from the current snapshot's summary. Driver-scheduled maintenance is a later card.

In this design the guard is `read_resume_point` (§3.4). It reads the newest snapshot in the current
snapshot's ancestry that carries this query's stamp. If that stamped snapshot has been expired but the
property survives, it refuses with `RecoveryRequired(StampedSnapshotExpired)`, naming
`history.expire.min-snapshots-to-keep` as the fix.

**Q11 · file and rate sources — ruled by the owner (2026-10-05), restated.** The Iceberg source is the
product feature. The rate source is a test-only helper, outside the public surface. A file source is a
later, dated card. The harness (§5) is Rust over Iceberg tables and needs neither source.
`readStream.format(x)` for any `x` other than `"iceberg"` refuses `NOT_IMPLEMENTED` with
`{"feature": "readStream.format(<x>)"}` (MBE-7).

**`QueryId::derive`.** It is `Uuid::new_v5(&Uuid::NAMESPACE_OID, b"repark.cdc.query-id.v1")` used as the
namespace, applied to the canonical bytes:

```text
sink table uuid (16 bytes) || 0x00 for no name | 0x01 + u32-be length + UTF-8 name
```

Keying on the sink's uuid rather than its name keeps the id stable across a rename or a catalog alias, and
it needs no store (R-6). Two queries that feed one sink need distinct `queryName`s. A query whose input set
changes refuses (`InputsChanged`).

**`Generation`.** It is `1` on a query's first commit and is inherited on every restart. No 1.7 surface
changes it: a reset is a new `queryName` (Q5), and a reset surface is reserved by name. The field still
rides on every commit. A resumed driver refuses to advance a record whose generation differs from the one
it resumed with (CC-9, MBE-11).

  least one whole file (R11: three batches of one file; R12: `max-rows=1` still yields two batches of 3

is at most one entry per sink; a second `enter` gets `SinkBusy`.

**`claim`** runs at each named commit site with the `Table` the transaction starts from, so the base is
`H = table.metadata().current_snapshot_id()`.
- MB-2a returns the stamp.
- MB-2c first runs the **epoch check** on that same `table`. If `read_resume_point` already shows the epoch
  under this run, the result is `AlreadyCommitted`. Under another run it is `Fenced`. A generation other
  than the resumed one gives `GenerationMismatch`.
- A second claim for one epoch gives `SinkCommittedTwice`.

- `write_options.rs:433` (`commit_append_with_summary`);
- `snapshot_commit.rs:174` (copy-on-write);
- `snapshot_commit.rs:408` (merge-on-read).

**`read_resume_point`.** It does no IO: it reads table metadata already loaded. It walks the ancestry from
the current snapshot to the newest snapshot whose summary carries `QUERY_ID_KEY = query`, then compares
that record with the property.
- Equal records: return the record.
- Both absent: return `None` (first run).
- A mismatch: `RecoveryRequired(OffsetMismatch)`.
- Property present but no stamped snapshot retained: `RecoveryRequired(StampedSnapshotExpired)`.
- A format above 1: `UnsupportedOffsetFormat`.

**`resolve_unknown_outcome`** (MB-2c) is the silver-s0 C-008 walk. The fork reconciles first, by its own
attempt snapshot ids (`fork:crates/iceberg/src/transaction/mod.rs:430`). If the outcome still surfaces as

`engine.operation-id` (`crates/repark-iceberg/src/write/merge/mod.rs:86`) and, failing that, on
`(query-id, epoch)`.
- Found: return its id.
- Absent: `RecoveryRequired(CommitOutcomeUnknown)`.

It never re-submits, and never runs a replace.

## 7. The conditional fork ask

**F-APPEND-PIN-BASE-1** (proposed, not filed; OQ-4).
- **The ask.** `FastAppendAction` and `MergeAppendAction` gain `validate_from_snapshot(i64)` and
  `validate_no_concurrent_data()`, default off. When they are set, `validate` fails non-retryably if the
  refreshed base holds an `Append`, `Overwrite` or `Delete` snapshot on the target ref newer than the
  pinned id. `Replace` is excluded. The operation stays `Append`.
- **Pins.** A racer's append between load and commit fails the pinned commit. An unrelated `replace` does
  not fail it. With the option unset, today's re-base still happens.
- **Mutation.** Dropping the check turns the first pin red.

It is the narrow form of silver-s0's `F-SILVER-PIN-BASE` candidate (`task/ledgers/staging/silver-s0-ledger.md`
C-008). It is filed only if DM-6 shows branch A fails.
